1. Why

Two capabilities e-footprint lacks today:

  1. Keeping a record as systems evolve. A modeled system changes constantly — jobs get optimized, journeys appear, infra migrates. Today each change silently overwrites the model; history is whatever JSON files someone happened to keep. Nothing connects "the footprint dropped" to "because we shipped the caching release".
  2. Modeling systems that evolve into the future. A roadmap of planned implementations, with assumptions about the world (grid carbon intensity, AI efficiency), evaluated as a footprint trajectory — the what-if simulation capability, reintroduced in a more flexible form than the deleted simulation_date API.

The product frame that keeps this decision-tooling rather than compliance reporting: simulate → act → verify. Every planned change carries a predicted footprint effect; after shipping, calibration measures the realized effect. The tool closes the loop that "simulate before you act" opens.

Why simulation_date was deleted rather than fixed: it fused a change into the live system as a dated mutation — the change was never inspectable data, only one hybrid half-old-half-new system existed, and the calculation engine had to know about dates of change. Every design decision below is downstream of not repeating that.

2. The two time axes

Modeled time is the hourly axis the engine computes over — hourly_occurrences(t), footprint(t). System-version time is the axis on which the description of the system changes: a deploy, an optimization, a new journey. A System object is the physics of the service at one version; the two axes touch at exactly one join point — an entry's effective_from date says from which modeled-time hour its version applies.

Separating the axes turns every use case into a quadrant — the deleted feature could only express one diagonal of this table:

current / past systemchanged system
past usagehistorical reconstruction counterfactual ("what would last year have cost with the optimization?")
future usagebusiness-as-usual projectionroadmap simulation
Classification criterion: the version axis carries your team’s decisions (code, infra, journey structure, calibrated physics). Evolving world context — grid carbon intensity paths, provider-side AI efficiency — belongs on modeled time, as input series extending into the future. Test: would you put it in the team’s changelog and hold the roadmap accountable for it?
Why world context must not be version entries — and two parked ideas

Three reasons. (1) Events vs trajectories: version entries are discrete (before/after); grid intensity is a continuous path — encoding it as entries chops the timeline into artificial segments. (2) Attribution: the ledger is the team’s changelog; if the grid getting cleaner lands next to your caching release, "the system changed" becomes meaningless and predicted-vs-realized verification is impossible. (3) Scenario orthogonality: world trajectories arrive as wholesale pathways (ADEME/IEA scenarios) you want to swap under the same roadmap — a third independent dimension (system version × usage scenario × world scenario).

Parked idea #1: country carbon intensities as modeled-time series (today they are constants on Country) — the library evolution this classification implies. Until then, piecewise version entries are a legitimate, labeled workaround.

Parked idea #2: a decay function reducing a given AI model’s impact if kept across time (provider-side efficiency drift). Boundary case by construction: the same parameter changes as world context (provider silently improves) or as a decision (team swaps models) — the changelog test decides which channel each occurrence uses.

3. Timeline entries

One entry = one cause — a release, a decision, a discovered correction — carrying 1..N atomic changes. Never one entry per changed value: verification targets "the caching release", not twelve scattered numbers.

{
  "recorded_at":    "2026-03-14",          // when it entered the ledger
  "effective_from": "2026-03-12",          // when it applies on modeled time
  "kind":   "change",                      // or "revision" (knowledge changed, system didn't)
  "label":  "Search results caching (release v2.31)",
  "status": "calibrated",                  // observed | calibrated | planned | hypothesis | drift
  "evidence": {"release": "v2.31.0", "fit": "calibration 2026-03 diagnostics"},
  "changes": [
    {"object": "job-search", "attr": "compute_needed", "op": "set", "old": "…", "new": "…"}
  ],
  "predicted_effect": null,                // filled for planned entries, at planning time
  "realized_effect":  {"footprint_delta": "-11.8%", "measured": "2026-04 calibration"}
}

A future entry is the same object with status: planned, a filled predicted_effect and an empty realized_effect — completed later by calibration. The simulate → act → verify loop is literally these two fields on the same record. Past and future differ only by status — the coverage-table discipline (observed / calibrated / hypothesis / planned) extended in time.

Details — atomic change kinds, revisions, state-carrying parameters

Three atomic change kinds, all expressed on the JSON representation (object id + attribute + value), which is why none of this needs engine surgery: attribute (old → new on an existing object), add (new object + its attachment point), remove (object retired).

Change vs revision. A recalibration can move a parameter with no deploy behind it — reality didn’t change, the estimate improved. Recording it as a change would put a phantom step in the footprint history. So kind: revision exists: appended to the same chain (never editing the file), with effective_from in the past. Replay orders by effective_from (ties by recorded_at), so revisions reshape the past while the ledger stays append-only. The deploy/change log is what distinguishes the two mechanically: a parameter jump with a matching release is a change; without one, a revision.

Bitemporality for free: because every entry has both dates and the chain is append-only, "what did we believe on date X about date Y" is answered by replaying only entries with recorded_at ≤ X. Delivered reports pin the ledger position they were computed from; later restatements are then detectable and explainable as a diff of beliefs.

State-carrying parameters. Inputs that represent accumulated state — today essentially base_storage_need (initial stored data) — obey special rules, flagged by class-level metadata (a state_carrying tag in the SSOT class metadata): their absolute level is owned by the accumulation dynamics (§5), so entries touching them use op: "adjust" for decisions ("purged 10 TB of logs": −10 TB composing with the handoff) and op: "set" only for revisions that re-anchor the state to a measurement ("actual storage is 47 TB, model said 52" — and the 5 TB gap is itself a finding about the modeled growth rate).

4. The file

Lean, single source of truth: the base system in full, then only entries. Later versions are materialized by replay, never stored — the calculation graph is derived by the engine from any materialized description, so nothing is lost. Computed results live in a separate, honestly-named cache section:

{
  "base_system":  { …full description — the only one stored… },
  "entries":      [ …the append-only ledger (§3)… ],
  "version_hashes": { "v2": "…", "v3": "…" },     // integrity: replay must reproduce these
  "cached_evaluations": [
    {"segment": "v3", "window": "2026-03-12 → 2026-06-20",
     "efootprint_version": "22.3.0", "ledger_position": "…",
     "impact_sources": "…hourly series…", "end_state": {"storage-main": "47.2 TB"}}
  ],
  "restatements": [ …condensed corrections of settled numbers (§5)… ]
}
Leanness rule: redundant truth is forbidden; redundant caches with an explicit invalidation rule are how performance is bought. Deltas are the truth; every materialized system and every computed series is a cache.
Details — event sourcing, integrity checks, the inverted git trade-off

This is the event-sourcing pattern: entries are the event log (truth), the materialized current system is a view (cache), cached evaluations are the read model. The pattern’s standard answers apply to replay determinism, view invalidation, and retroactive events (our revisions).

Integrity without stored snapshots: a hash of the materialized description per version (32 bytes instead of a full snapshot) — replay must reproduce it. And the undeclared-drift check is a process, not a storage layer: at each calibration ingestion, the freshly fitted description is diffed against the materialized current version; anything not explained by declared entries becomes a new entry labeled drift, cause unknown — a finding, not an error.

Git chose the opposite (store snapshots, compute diffs) because its diffs are semantically meaningless and random access must be fast. Here the situation inverts: entries are the semantically valuable artifact (dated, statused, verifiable decisions) and replay over tens of versions is instant — so diff-storage wins for reasons beyond leanness.

5. Segments, evaluation, settlement frontier

Replaying the ledger yields a version series — one system description per segment. Evaluating the timeline = materialize each version, evaluate it over its own window with the usage inputs sliced to that window, concatenate. Each segment evaluation is a plain e-footprint run; piecewise concatenation is the only new machinery.

Three consequences worth remembering cold:

  • There is no frozen archive. A past footprint is a model output about the past — revisable by a better calibration, a revision entry, or a library upgrade, like any output. There is only the current best estimate of the whole timeline; when settled numbers change, a condensed restatement record is appended (window, per-impact-source old → new, cause) — the same contract as the planned upgrade-drift feature. Delivered reports pin their own numbers; bitemporal replay reconstructs any past belief.
  • The frontier is a provenance boundary, not a freeze line. It separates observed-usage evaluation from forecast evaluation — driving status, hence trust, not immutability. It advances at ingestion time, which is the single operational moment where everything settles at once: observed usage replaces forecast for the new slice, its footprints are computed and cached, the fitted description is drift-checked, boundary state advances.
  • Segments hand off boundary state. e-footprint is stateless across hours except storage accumulation: segment k’s end cumulative storage initializes k+1, injected into the existing base_storage_need input by the materializer (per the state_carrying tag, §3). Each cached evaluation stores its end_state so any segment can be evaluated without replaying history.

6. Caching & interface architecture

LayerContainsInvalidation
Truthbase system + entries + hashes (kilobytes) never — append-only
Cached evaluationsper-(segment, window): footprints, version stamps, end_state; plus the current segment materialized in full with calculated attributes settled windows: rarely (revision, upgrade, late data) · future windows: constantly (any edited assumption) — same mechanism, different churn

No resident workers. Incremental recomputation does not require long-lived Python objects — it requires the computation cache to survive between edits, and the interface’s existing paradigm already provides that: each segment persists as a JSON blob with calculated attributes; deserialize → the calculated values return as trusted caches → an edit recomputes only descendants → reserialize. Editing the current segment while viewing the current segment costs exactly what the interface costs today. The N-segment cost appears only when a timeline view is displayed — where the pull engine’s pay-on-view semantics apply. In notebooks, the same invariant is held differently: systems stay alive in the process, and System.fork()-style structural sharing addresses RAM.

7. Propagating a change

There is no cross-segment dependency graph to invent — the ledger is the cross-segment dependency structure. Two layers:

  1. Shadowing (ledger level, kilobytes, no systems loaded): a later segment receives an edit iff no intervening entry re-sets the same (object, attribute). Output: a patch set per segment, often empty.
  2. Within-segment (engine level, existing machinery): for each affected segment, load its blob, apply the whole patch in one batched ModelingUpdate, let the dependency graph recompute descendants only, reserialize.
Details — the axis asymmetry and the chronological loop

The propagation rule depends on which axis the edit lives on. Version-axis edits (entry changes) propagate by shadowing. Modeled-time input edits (a revised usage forecast, a world trajectory) are not entries at all — they patch every segment whose window overlaps the changed part of the series.

The loop runs chronologically only for boundary state: after recomputing segment k, its end-state is compared to the stored handoff; if moved, "initial storage state" is added to k+1’s patch even if k+1 was fully shadowed. Most edits don’t touch storage flows, so the chain stops immediately.

8. Performance posture

The interactive path never relies on cold rebuilds: shadowing bounds which segments recompute, incremental recomputation bounds what recomputes inside each, and the pull engine defers everything unviewed. The honest cost model for the cold path:

  • A numpy element-wise op costs fixed per-call overhead + n × per-element. An hourly year (8,760 elements) sits near the crossover — and e-footprint ops add Pint and ExplainableObject bookkeeping to the fixed part, so evaluation is plausibly overhead-dominated at our sizes. Consequence: splitting a horizon into k segments costs closer to k× one run than 1× (the element math is the same; the per-op overhead multiplies). With k ≈ 5–10 and single runs in seconds: cold full-timeline rebuild is seconds-to-tens-of-seconds — an explicit action, not a keystroke.
  • Open measurement before asserting more: time the same system evaluated over 1 week vs 1 year. Barely moves → overhead-dominated (segmentation ≈ k×); scales with hours → element-dominated (segmentation ≈ free).
  • The real cost is RAM, not CPU (N live systems in notebooks; N blobs in Redis) — and adjacent versions differ by a handful of objects. Copy-on-write forking (System.fork()) is the answer, and it is already wanted by calibration fit loops: two independent use cases converging on one primitive — the strongest prioritization signal this exploration produced.

10. Open questions

  1. Attribution methodology. The causes stay separable by design (usage / system / methodology / world), but decomposing a footprint change into their contributions is undesigned: sequential substitution has an ordering problem, interaction terms exist. The calibration reconciliation-bridge style is the candidate. Meatiest open point.
  2. Branches and scenarios. "A simulation = an alternative entry sequence from a common prefix" is asserted, not designed: representation in the file, lifecycle (ephemeral what-if vs saved roadmap variant), and what compare_to between two timelines outputs.
  3. The authoring workflow. Who writes entries in practice — calibration tooling proposing them from diffs + the deploy log, a human curating labels and causes? The minimal-friction loop matters more than the format for adoption.
  4. Freezing predicted_effect. Computed by evaluating a branch at planning time — but under which usage assumptions, and is it re-baselined when upstream assumptions change before shipping?
  5. The edge paradigm. All of the above assumes the web/demand-driven side. Whether fleet models need the same ledger — and whether fleet growth is a version entry or a modeled-time input — is unexplored.

11. Path to adoption

  1. Incubate through calibration missions. Recurring calibrations already produce dated results; a small diff tool over consecutive results + the client’s deploy log yields proto-entries by hand. Two missions of that are the requirements probe — the same pattern that gates System.fork().
  2. Run the §8 measurement (1 week vs 1 year evaluation) before committing to a performance posture.
  3. Land the prerequisites that are wanted anyway (fork, pull engine, calibrated status) — the timeline then becomes a thin layer over them.
  4. Only then spec it, as a library feature or a package on the JSON seam — the exploration deliberately does not decide which.
