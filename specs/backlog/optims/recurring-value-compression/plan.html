Recurring-value compression — Implementation plan

Status: Plan — under review · 2026-08-05 · Technical-plan-only workflow approved by the user

1. Outcome and approach

ExplainableRecurrentQuantities currently serializes each float32 array as the decimal-text representation of a Python list. Replace that payload with the same lossless storage shape already proven for hourly quantities: contiguous float32 bytes, Zstandard compression, then Base64 for JSON transport. The new discriminator is compressed_recurring_values; current-version readers accept that canonical shape only, while the version migration converts older recurring_values payloads before object hydration.

Compression remains local to the recurrent quantity type. Small static compression/decompression helpers mirror the hourly implementation rather than introducing a cross-type abstraction. Metadata, units, formulas, sources, and the 168-hour recurring-pattern invariant are unchanged.

The hot-path requirement is a gate, not an aspiration: full snapshot serialization and exact-version loading must not regress on the canonical 13-model corpus at /Users/vinville/dev/e-footprint-full/json_files_that_should_load_and_open_results_without_failing_in_interface.

4. Ordered implementation

  1. Add recurrent float32 compression/decompression helpers that mirror the hourly codec and prove exact array round-trip independently.
  2. Switch recurrent JSON registration, reading, and writing to compressed_recurring_values; preserve all base-class metadata and formula behavior.
  3. Add the recursive 23→24 migration and version bump. Convert, do not drop, recurring values because they are authoritative model inputs.
  4. Update unit, migration, and integration coverage; regenerate only fixtures whose owning tests require the new current-version representation.
  5. Run focused tests, the canonical-corpus size/hot-path benchmark, the full pytest suite, and mkdocs build --strict.
  6. Update persistence documentation and the changelog with the measured final results.

5. Acceptance and performance gates

  • Every finite float32 array round-trips bit-for-bit with the same unit, label, source, confidence, comment, and serialized formula relationships.
  • Every supported pre-v24 model upgrades without retaining a recurring_values key.
  • A current-version full snapshot round-trips through system_to_json → JSON → json_to_system without recomputation or semantic drift.
  • The canonical corpus remains 13/13 loadable and result-ready.
  • Indicative corpus targets, to be remeasured after implementation: logical JSON decreases from 7.87 MB toward 7.28 MB; Redis/pickle payload decreases from 6.16 MB toward 5.56 MB.
  • Repeated codec measurements show no regression in full snapshot serialization or exact-version loading. The investigation baseline for 351 arrays was 8.18 ms → 0.27 ms encode and 5.15 ms → 0.30 ms decode; final numbers are recorded, not asserted with a flaky wall-clock unit test.
  • Full pytest and strict documentation builds pass.

6. Risks and mitigations

  • Endianness/platform ambiguity: the project currently serializes native float32 bytes for hourly quantities. Keep the recurrent codec identical and test on the supported Python/CI matrix.
  • Read-only NumPy buffer: decoding through np.frombuffer follows the hourly path; copy only if recurrent mutation tests demonstrate a writeability requirement.
  • Incomplete migration traversal: use one recursive JSON-tree conversion and test nested formula and dict shapes rather than enumerating modeling classes.
  • Accidental compatibility shim: v24 runtime registration recognizes only the new key. Legacy support belongs exclusively to the version handler, consistent with the constitution.
  • Misleading JSON-only win: record both JSON-budget and actual Redis/pickle measurements.

7. Alternatives rejected

  • Store a JSON number array: removes the quoted string but retains expensive decimal conversion and most bytes.
  • Run-length encoding: excellent for constants but data-dependent and weaker for arbitrary weekly patterns.
  • Compress the whole system payload: obscures random inspection, changes cache integration, and is broader than the identified hotspot.
  • Accept both keys in the live decoder: creates a compatibility branch forbidden by the project policy; migration is the single old-format boundary.

8. Constitutional and architectural notes

This remains JSON and uses existing NumPy/Zstandard dependencies, so no constitutional principle changes. It is a schema change: constitution §2 requires a migration handler, major version bump, round-trip coverage, full tests, strict docs, and changelog entry. Compression stays in the framework layer; the API migration layer may depend on it, preserving the required dependency direction.
