Apache-2 relicense — Implementation plan

Status: Plan — DRAFT (produced with the spec because the kickoff was design-rich; refine at spec-plan stage) · 2026-07-03 · Spec: spec.html

1. Approach

Two workstreams. Workstream A (code, ships first): make the AGPL boaviztapi package an optional extra — valuable regardless of the license decision (lighter default install, cleaner tree, explicit self-hosting story). The code is already structured for it: call_boaviztapi() uses the hosted HTTP API as primary path with a 7-day cache, and touches the package only behind the USE_BOAVIZTAPI_PACKAGE env var or as automatic fallback on web failure (boaviztapi_utils.py:60-76), with the import already function-local (:111-115). Workstream B (governance): contributor consents, PS sign-off, Boavizta conversation, license swap mechanics, DCO, announcement. B gates on A being merged (a relicense with a required AGPL dependency would be cosmetic).

4. Cross-cutting concerns

  • Tests: suite must pass with and without the extra; add explicit tests for the guarded-import error message and the base-URL override; CI license-audit gate.
  • Migrations: none (no JSON schema change).
  • Docs: README, mission.md, mkdocs pages mentioning license or Boavizta setup; announcement post (framing: "the license should never be the reason e-footprint isn't embedded"; Boavizta paragraph: their AGPL methodology core stays protected while e-footprint extends its reach over HTTP).
  • Sequencing: A merges anytime; B ships only after (1) PS legal sign-off, (2) consents complete, (3) Boavizta informed. The calibration feature can start under AGPL and inherit the new license transparently — it should not wait.

5. Risks

  • Contributor unreachable or declines — rewrite their hunks (small counts make this feasible); worst case delays workstream B only.
  • Boavizta discomfort (their projects lean AGPL) — mitigation: the HTTP-consumption framing above, plus MPL-2.0 as the named fallback if reciprocity turns out to matter politically.
  • Hosted-API dependence becomes more visible once the package is optional — mitigation: existing 7-day cache, bundled snapshot, documented self-hosting (Docker), and the extra for those who want in-process fallback.
  • Perception risk ≈ zero: permissive-ward relicenses are welcomed by users; the Elastic/HashiCorp backlash pattern applies to the opposite direction.

6. Alternatives considered

  • MIT / BSD-3 — rejected: no explicit patent grant; Apache-2 is the corporate-hygiene standard and matches the interface.
  • MPL-2.0 — the serious runner-up: file-level copyleft targets exactly the "improved core sold proprietary" worry while freeing integrators. Rejected as primary because most corporate policies still put MPL in a "reciprocal — review required" tier (friction at exactly the target adopters), the protection is hard to enforce in practice, and the peer ecosystem (Cloud Carbon Footprint, Kepler, Scaphandre, Impact Framework) is Apache-2/MIT. Retained as the named fallback.
  • Stay AGPL + case-by-case dual licensing — rejected: per-deal friction, scales with PS effort, does nothing for organic adoption.
  • BUSL / fair-source — rejected: contradicts the mission's collaboration ethos and the consulting business model (missions, not licenses).

7. Constitutional notes

The constitution is silent on licensing; no amendment needed. Constitution §1.2 ("no external callers besides e-footprint-interface") is unaffected — a permissive license invites external users but promises them nothing, which should be stated in the announcement ("no API stability guarantees for third parties yet"). specs/mission.md is the downstream artifact that must follow.
