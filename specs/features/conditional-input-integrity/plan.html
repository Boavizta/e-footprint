1 · Shared dependency descriptions

Keep conditional_list_values as the authoritative declaration. The existing get_init_signature_params() resolves constructor annotations and already caches them. Derive dependency descriptions from those declarations and annotations; each description identifies a dependent input, its controller type/attribute, and the relationship path between them.

efootprint/abstract_modeling_classes/conditional_inputs.py Proposed conceptual descriptor; exact names to be refined

controller_type: type
controller_attribute: str
dependent_type: type
dependent_attribute: str
relationship_path: tuple[str, ...]

Example: video API / model_name
    → video job / resolution
    through ("external_api",)

Build lookups for the final controlling attribute and every relationship segment that can redirect the path. A controller change resolves only the active referring objects prescribed by those descriptions. Longer paths reverse only their named hops; they do not continue into unrelated ancestors. Same-object dependencies use the same contract.

The existing ContextualModelingObjectAttribute carries its referring owner and attribute. Use active relationship bindings, excluding detached wrappers. Do not add a persistent per-model subscription index unless planning shows that existing backlinks cannot satisfy bounded discovery.

[PLAN-UPDATE-01] — PROPOSED

Cache derived class descriptions, without holding model instances or duplicating declarations on controllers. Resolve actual dependents from current relationships during edits. Generic framework registration must handle subclass declarations and invalidate cached descriptions when registered metadata changes; do not import the concrete class catalog into the framework.

This replaces the earlier broad reverse-ancestor traversal proposal. A shared API still requires checking every affected job; the improvement is avoiding unrelated paths and repeated interpretation of class metadata.

Expose a small shared surface for path resolution, controller/dependent discovery, and allowed values under candidate changes. The candidate query must follow proposed relationship replacements and proposed controller values without mutating the live graph.

Reuse input_values_match(). Preserve the existing branch semantics: a missing branch is unrestricted, an empty branch permits no values, and option order is the declared order. A library input reference should identify the actual object and constructor attribute; adapt it to interface IDs rather than moving the interface's catalog or configuration into the framework.

2 · Change a library input

Current evidence: changing an API from OpenAI / sora-2-pro to ByteDance / seedance-1.0 while retaining a job at 1080p succeeds. A fresh impact calculation also succeeds. These are local diagnostics from 2026-10-12, not guarantees about future catalog contents.

ModelingUpdate currently calls check_belonging_to_authorized_values() only for new_sourcevalues. Its attributes_with_depending_values() is class-local, so the API's change never checks an unchanged job resolution.

Capture changed input addresses before old values detach. Discover conditional dependents through the shared descriptors, apply the complete batch, and validate affected inputs against the final state within the existing transaction try/rollback boundary. Use one shared choice-validation implementation for directly changed values and unchanged affected dependents.

A rejected batch uses rollback() and restores inputs and relationships before recomputing the existing eager boundary. Validate before footprint guards run on an invalid final combination. Valid batches can change Provider, Model and every necessary Resolution together, in any input order. Conditional failures must identify the affected object/input, unsupported value, controlling choice and allowed values, including a clear explanation when no value is allowed. Use existing error presentation rather than a new recovery workflow.

This input validation must work for standalone objects and cold objects. It cannot depend on dependency edges learned by footprint getters. Preserve pull_eagerly() for other guards instead of substituting a video-specific computed guard for generic conditional validation.

3 · Replace a relationship

Current evidence: assigning a new API to a warmed video job retains its unsupported 1080p resolution and computes fresh impacts. Type checking runs through parse_changes_list(), but the modeling-object replacement is absent from the explainable-value validation loop.

Index the relationship segment as a trigger. Replacing the API link must validate the job's resolution against the new API's model, even when neither API model is changed. For longer paths, replacing an intermediate relationship has the same effect.

Candidate queries and final-state validation must agree when one batch changes an API model and redirects jobs. Detached old links must not remain validation targets. Subsequent changes to the old API must not validate redirected jobs, while subsequent changes to the new API must find them. Keep the existing collect_newly_linked_mod_objs() guard behavior for genuinely newly attached objects.

No new job-redirection control is proposed in the interface. Direct library assignment and explicit batched replacement are supported operations.

4 · Save in either editor

Today prepare_input_changes() converts submitted fields and preserves omitted provenance. Normal editing invokes edit_object_from_parsed_data() for one owner; only EditSimplifiedInputUseCase.execute() gathers conditional changes across owners.

[PLAN-UPDATE-02] — PROPOSED

The library rejects incompatible batches and never chooses replacement values implicitly. Extract the existing editor repair policy into one interface domain service used by normal and simplified edits. It uses library queries to keep valid choices or select the first allowed value, and returns structured automatic-change information.

Prepare the whole submitted edit before reconciling dependent choices. Keep submitted values distinguished from generated replacements: a conflicting expressly submitted dependent is an error, rather than an invitation to overwrite it. Chain candidate changes until affected choices are coherent, preserving labels, sources, confidence and comments on generated replacements through the usual preparer.

Submit one multi-owner transaction, then persist once at the owning use case's final boundary. EditObjectUseCase.execute() and the simplified use case consume the same automatic-change records. Rejection discards request-local metadata and publishes no partial save.

Return affected fields whose options changed even when their values were retained. Present notices through existing feedback conventions; keep value changes separate from metadata-only changes. Trace composite pre-edit hooks during planning so this extraction does not broaden or break unrelated nested-object edits.

For the normal API edit, the browser still submits the user's explicit Provider/Model choices on Save. The shared service repairs linked job resolutions; it does not silently replace a conflicting Model that the user explicitly submitted.

5 · Configure and render choices

build_catalog() currently reconstructs controller/dependent edges using the interface's resolve_input_path(). Consume library descriptions and migrate the duplicate resolver's callers. Keep input eligibility, forced companion inclusion, help and persisted configuration in the interface.

complete_selection() keeps its interface policy, using the shared edges. The library does not inherit Simplified inputs selection rules.

generate_dynamic_form() independently interprets branches for fixed edit references and creation-time reference candidates. Use the shared allowed-values query for those contexts, retaining existing labels, field order and one-hop browser lists.

Current mismatch: the resolved-options branch filters away unsupported resolutions, while select_str_input.html marks no option selected. Native selection then displays the first option despite a different stored value. Prevent newly introduced incompatible states through transaction validation and editor reconciliation; verify that accepted states render their saved choice without adding an invalid-file widget.

6 · Upgrade older files to version 26

[PLAN-UPDATE-03] — ACCEPTED

Ship this feature as library version 26.0.0 and add a narrow 25→26 migration for incompatible historical video-job resolutions. Live conditional validation belongs in ModelingUpdate; do not add a global import validation pass, footprint-time conditional validation or special recovery UI.

Automatic dependent updates during normal and simplified edits remain in scope. The migration is a version-bound correction of the known legacy defect, not implicit repair during ordinary library updates.

The current upgrade_system_dict_to_current_version() dispatches handlers across major versions. Add the proposed handler to VERSION_UPGRADE_HANDLERS with key 25, and advance efootprint/version.py and pyproject.toml to 26.0.0 during implementation.

efootprint/api_utils/version_upgrade_handlers.py Proposed handler contract; not implemented

upgrade_version_25_to_26(system_dict, efootprint_classes_dict=None)
    for each serialized video job:
        resolve its linked API and saved AI model
        obtain that model's allowed resolutions from the class metadata
        keep a supported resolution unchanged
        otherwise, if compatible options exist, replace only its value
            with the first allowed resolution
    return system_dict

Operate on serialized inputs using the supplied class registry and existing conditional-choice metadata. Do not hydrate temporary model graphs or hard-code the EcoLogits resolution catalog. Iterate the serialized video-job collection directly so disconnected jobs receive the same correction. Preserve labels, source references, confidence, comments, API relationships, valid values and other inputs. The handler does not repair provider/model pairs or arbitrary malformed JSON.

The existing json_to_system() uses version mismatch to stop trusting old computed caches and retains eligible values as a historical baseline. Reuse that behavior so calculations use repaired inputs; do not add another cache-clearing or import recovery mechanism.

Files from earlier supported releases reach this handler through the existing upgrade chain. Version 26 files do not rerun it. The snapshot structure remains unchanged; the new major release carries the specific input correction and hardened mutation behavior.

Align the interface's publishable dependency with version 26 before merging the coordinated implementation. Preserve the current editable dependency and pre-existing lockfile edits during local development. Release preparation does not authorize package publication or deployment.

Planning questions

  • Registration and cache scope: choose the smallest generic registration mechanism. Confirm inherited and polymorphic constructor paths, test-time metadata changes, and dynamic class import behavior without introducing a concrete-builder import.
  • Candidate and affected-input contract: finalize input identity and result shapes shared by validation, repair, configuration and forms. Include intermediate relationship triggers and retained dependents whose options changed.
  • Normal edit integration: trace notices, affected field refresh and composite pre-edit hooks before fixing module boundaries. The provisional service filename is not an approved architecture choice.

The version 26 migration and transaction-only validation boundary are accepted. Other design proposals still need planning review; no tasks, briefs, application edits or application test runs are produced by this specification stage.
