Conditional input integrity

Feature spec · Proposed changed files

Enforce conditional choices at the library's live-update boundary, then share the interface's existing repair policy across both editors. Derive affected inputs from authoritative declarations and current relationships; keep repair choices and save feedback in the interface.

Library source paths are relative to e-footprint; interface ownership is identified explicitly. Linked proposed names are design sketches until implemented. No application implementation or task list is part of this stage.

1 · Shared dependency descriptions

conditional_list_values stays the single declaration of dependent choices. The new conditional_inputs.py derives paths and reverse triggers from it and the runtime constructor annotations returned by get_init_signature_params(). It owns no concrete class catalog and stores no model instances globally.

efootprint/abstract_modeling_classes/conditional_inputs.py Proposed contract; illustrative Python

@dataclass(frozen=True)
class InputRef:
    owner: ModelingObject        # actual object, never a contextual wrapper
    attribute: str              # constructor input name

From the declaration to the trigger index

For this example, Job and API are shortened class names. register_conditional_inputs(cls) reads the dependency string directly from the job's metadata, then resolves the API type from the job constructor annotation. It adds a routing entry for each input whose change can redirect or alter that dependency's controller:

# register_conditional_inputs(cls) reads the existing declaration:
for dependent_attribute, declaration in cls.conditional_list_values.items():
    path = declaration["depends_on"].split(".")
    # Resolve each relationship type from constructor annotations.

# Example metadata read for Job.resolution:
Job.conditional_list_values["resolution"]["depends_on"]
# -> "external_api.model_name"
get_init_signature_params(Job)["external_api"].annotation
# -> API

# Private module-level dictionary after Job is registered:
_trigger_index = {
    (API, "model_name"): [
        {
            "dependent_type": Job,
            "dependent_attribute": "resolution",
            "reverse_hops": ((Job, "external_api"),),
        },
    ],

        {
            "dependent_type": Job,
            "dependent_attribute": "resolution",

        },

Each index key identifies the owner type and input that changed. Its value is a list of ordinary dictionaries, each naming an affected dependent class/input and the route to its owner. Each entry's reverse_hops is an ordered tuple of (referring-owner type, relationship input name) pairs, followed from the changed object back toward the dependent owner:

  • An API model-name edit starts at the changed API. The single hop finds jobs referring to it through their API relationship; check each reached job's resolution.
  • A job's API replacement starts at that job. The empty tuple means its owner is already known; check its resolution directly, using the new API.

The private _trigger_index dictionary lives at module scope in conditional_inputs.py. It stores classes, input names and reverse hops. Dependency paths and choice mappings remain in cls.conditional_list_values; runtime queries read that declaration directly. Actual affected jobs come from current backlinks when a query or update runs, so every job sharing an API uses the same routing entry.

Dependency paths follow individual object relationships from the dependent object to its controlling input. Constructor annotations identify the types along that path, including inherited inputs and subclass relationships. If an annotation permits several modeling-object types, derive the route for each type; an optional absent relationship still reports an actionable path error when a query needs it. Every relationship and the final controlling input must be declared in the reached class's constructor. Report an unknown relationship or input with the declaring class and full dependency path. Paths through lists or dictionaries remain outside the feature.

[PLAN-UPDATE-01] — ACCEPTED

Read declarations directly from cls.conditional_list_values. Add ModelingObject.__init_subclass__() in efootprint/abstract_modeling_classes/modeling_object.py; its sole registration call is register_conditional_inputs(cls) in conditional_inputs.py. Python invokes the hook when each subclass is defined, normally during module import. Current declarations follow the existing constructor-annotation convention, so their relationship types are available then.

efootprint/abstract_modeling_classes/modeling_object.py Proposed method added to the existing class

class ModelingObject(metaclass=ABCAfterInitMeta):
    def __init_subclass__(cls, **kwargs):
        super().__init_subclass__(**kwargs)
        from efootprint.abstract_modeling_classes.conditional_inputs import register_conditional_inputs
        register_conditional_inputs(cls)

register_conditional_inputs(cls) returns no value and performs these steps:

  1. Iterate cls.conditional_list_values. A class without conditional declarations needs no routing entries.
  2. Resolve the relationship types with get_init_signature_params(), verify each relationship and final controlling input, and report malformed declarations with their class and complete path while the class is being defined.
  3. Add the derived routing dictionaries to the module-level _trigger_index, keyed by the type/input of the final controller and each replaceable relationship segment. Keep the branch mapping on its original class.

Queries use the dictionary directly along the changed owner's class hierarchy. Lookup costs one dictionary read per type in that hierarchy, followed by the matching reverse paths and affected inputs. A later class definition extends the dictionary and is visible on the next query. This keeps lookup bounded without a second rule representation or a controller lookup cache.

Read inherited declarations from each effective subclass. A reached dependent owner must have the class recorded in its routing entry, so an overridden subclass declaration is not discovered through the parent's obsolete path. Read branch choices directly from their class metadata; the existing patches in the empty-branch regression remain visible. Dependency-path and signature tests use fresh class declarations.

Instance creation and hydration reuse the index built during class definition. _mark_live() keeps its existing instance-lifecycle responsibility. The routing dictionary is runtime state containing no modeled instances; registration validates declarations, while conditional input values remain checked at the transaction boundary.

Query contracts used by the walkthrough

All four query functions below belong to the proposed efootprint/abstract_modeling_classes/conditional_inputs.py. The examples use the shortened video class names introduced above; option examples follow the current class metadata. These functions query inputs and dependency declarations without attaching values or running calculated attributes.

resolve_input_path() — find the controlling input on a particular object

resolve_input_path() starts from an actual modeling object, follows the supplied dependency path and returns an InputRef containing the reached owner and final attribute name. The path is the dotted string stored in the declaration's depends-on field.

efootprint/abstract_modeling_classes/conditional_inputs.py Proposed contract and example; illustrative Python

resolve_input_path(owner, path, candidates=None) -> InputRef

# Given: job.external_api refers to api.
resolve_input_path(job, "external_api.model_name")
# -> InputRef(api, "model_name")

candidates = {InputRef(job, "external_api"): other_api}
resolve_input_path(job, "external_api.model_name", candidates)
# -> InputRef(other_api, "model_name")

Candidate changes. The optional candidates argument maps InputRef addresses to proposed replacement values or related objects. At each relationship, resolve_input_path() uses its proposed replacement when present, otherwise its live value. Wrapped objects are normalized to their actual owner. The example leaves the live job linked to the original API.

Errors and callers. resolve_input_path() reports a missing relationship or unknown input with the complete path, because it cannot determine the controller address. It does not inspect branch choices. allowed_values() uses its returned address to read the controlling value; the interface catalog and form generator use the same address to identify the controller. Replace their interface resolver imports with this library function and remove model_builder/domain/conditional_inputs.py.

allowed_values() — get the choices for an input under live or proposed values

allowed_values() takes the address of an input, such as a job's resolution, and returns its effective allowed choices in declared order. The optional candidates mapping describes the proposed batch whose choices the caller wants to inspect.

efootprint/abstract_modeling_classes/conditional_inputs.py Proposed contract and example; illustrative Python

allowed_values(input_ref, candidates=None) -> tuple[ExplainableObject, ...] | None

# Given: job.external_api refers to api.
candidates = {
    InputRef(api, "provider"): SourceObject("bytedance"),
    InputRef(api, "model_name"): SourceObject("seedance-1.0"),
}
allowed_values(InputRef(job, "resolution"), candidates)
# -> (
#     SourceObject("480p (854 x 480)"),
#     SourceObject("720p (1280 x 720)"),
# )

How it obtains the choices. For a conditional input, allowed_values() reads the dependency path from cls.conditional_list_values, finds its controller address through resolve_input_path(), reads the candidate or live controlling value, and delegates branch selection to choices_for_controller(). A proposed relationship replacement is followed in the same way. An input with only a static list returns that list as a tuple.

Return meaning. A non-empty tuple contains the permitted values; an empty tuple permits no value; None means neither the applicable conditional branch nor a static list restricts the input. Ordinary type, unit and other domain validation still apply. A missing dependency path raises the path error from resolve_input_path().

Callers. Planned transaction validation compares the final input value with allowed_values(); the shared apply_input_edits() uses its result to retain a valid choice, reject an explicit conflict or select a replacement. Fixed-reference and Simplified forms use the same result to display current options. allowed_values() returns options without deciding whether the current value should be retained or replaced.

dependent_inputs() — find the next inputs affected by a change

dependent_inputs() takes a set of changed input addresses and returns a set of affected conditional-input addresses. It reads _trigger_index along the changed owner's class hierarchy, then follows only the reverse relationship hops in the matching entries. The optional candidates mapping makes discovery follow proposed relationship replacements.

efootprint/abstract_modeling_classes/conditional_inputs.py Proposed contract and example; illustrative Python

dependent_inputs(changed_refs, candidates=None) -> set[InputRef]

# Given: exactly job_a and job_b refer to api.
dependent_inputs({InputRef(api, "provider")})
# -> {InputRef(api, "model_name")}

dependent_inputs({InputRef(api, "model_name")})
# -> {InputRef(job_a, "resolution"), InputRef(job_b, "resolution")}

dependent_inputs({InputRef(job_a, "external_api")})
# -> {InputRef(job_a, "resolution")}

efootprint/abstract_modeling_classes/conditional_inputs.py Proposed direct lookup; no scan of other registered types

# Inside dependent_inputs(); changed_ref.owner is the actual object.
for owner_type in type(changed_ref.owner).__mro__:
    entries = _trigger_index.get((owner_type, changed_ref.attribute), ())
    # Follow each entry's reverse_hops, then add the reached input address.

The lookup includes ancestor types, so an actual API subclass finds dependencies declared against its parent API type. _trigger_index changes are read immediately. Reached input addresses are deduplicated before validation; no lookup result is cached.

What “next” means. dependent_inputs() follows one conditional rule: Provider affects Model, and Model affects Resolution. It does not recursively expand the whole conditional chain in one call. One rule may nevertheless contain several object-relationship hops, as shown in the bridge example.

Values and callers. dependent_inputs() discovers addresses without testing the values stored there. It includes a dependent whose current value remains valid because its options may have changed. Planned ModelingUpdate validation checks those addresses together with explicitly changed inputs. The shared apply_input_edits() follows the conditional chain by calling dependent_inputs() again for reached inputs, then uses allowed_values() to evaluate them in controller-before-dependent order. A returned address outside the changed set does not itself imply an automatic replacement.

choices_for_controller() — get branch choices when the controlling value is already known

choices_for_controller() takes the dependent class, dependent attribute name and an already-known controlling value. It reads cls.conditional_list_values and the class's static choice list directly, and returns the same effective choice tuple that allowed_values() would obtain after resolving an owner and controller.

efootprint/abstract_modeling_classes/conditional_inputs.py Proposed contract and example; illustrative Python

choices_for_controller(cls, attribute, controller_value) -> tuple[ExplainableObject, ...] | None

choices_for_controller(Job, "resolution", SourceObject("seedance-1.0"))
# -> (
#     SourceObject("480p (854 x 480)"),
#     SourceObject("720p (1280 x 720)"),
# )

Why callers need it. Same-owner creation forms have class metadata and proposed controller values before a dependent object exists. The version migration has the saved video API's model value and the video-job class. Both call choices_for_controller() directly, without creating a temporary job or hydrating a graph.

Branch semantics owned by this function. An undeclared branch means the controlling value was obtained successfully but has no matching entry in the conditional mapping. It adds no restriction from that conditional rule. This differs from a missing relationship, which prevents resolve_input_path() from finding the controlling input.

Conditional mapping for this controller valueResult from choices_for_controller()
A branch lists choicesReturn those choices in declared order, filtered by any static list restriction.
No branch is declaredReturn the static list if one exists; otherwise return None, meaning unrestricted by these choice lists.
An explicitly empty branch is declaredReturn an empty tuple, meaning no value is permitted.

choices_for_controller() matches both controller keys and allowed values using input_values_match(), preserving absence versus zero and authored timeseries equality. Both choice functions return metadata option objects for read-only use; prepare_input_changes() converts a selected replacement into an owner-specific value with preserved label and provenance.

2 · Change a library input

Scoped diagnostics on 2026-10-12 confirm that an OpenAI / sora-2-pro API can change to ByteDance / seedance-1.0 while its job retains unsupported 1080p. Today ModelingUpdate.__init__() validates only new_sourcevalues; the class-local attributes_with_depending_values() cannot find another object's unchanged input.

The existing check_belonging_to_authorized_values() delegates membership to allowed_values(). Keep passive-construction checks for fields already being assigned; remove the separate class-local dependent loop from live-update validation. This changes no construction or import-wide validation policy.

  1. Keep type/unit checks and no-op detection in parse_changes_list(). After it expands existing entangled changes, capture actual owner/attribute addresses before detaching old values. Collection-member pairs keep their existing entry validation and do not become wildcard conditional paths.
  2. Apply every normalized pair through apply_changes() and retain the existing invalidation wave.
  3. Inside the existing exception/rollback boundary, call dependent_inputs() on the changed addresses, then validate both changed choice-constrained inputs and the returned dependents using allowed_values() against the final graph. Deduplicate input addresses; validate each once against all final controller choices.
  4. Only then call pull_eagerly() for existing guards and configured outputs. Conditional validity does not depend on a guard or a previously learned calculation edge.

efootprint/abstract_modeling_classes/modeling_update.py Proposed contract; illustrative Python

changed_refs = capture_addresses(normalized_pairs)  # before old values detach
apply_complete_batch_and_invalidate()
try:
    affected = dependent_inputs(changed_refs)
    validate_choices(changed_refs | affected)        # final live inputs
    pull_eagerly(visited_slots)
except Exception:
    rollback()
    raise

A batch containing Provider, Model and all necessary Resolutions therefore succeeds in either submission order. A controller-only incompatible batch fails. The error names the dependent owner and input, submitted/current value, resolved controlling owner/input and value, and allowed choices; an empty branch says that no compatible choice exists. Explain that compatible corrections can be submitted in the same batch.

Use rollback() to restore values and links and re-invalidate/re-pull the existing eager boundary. Ordinary output caches may remain void and recompute on read; rollback promises coherent restored calculations, not an identical cache occupancy. Do not add a second computation-state snapshot. The owning lifecycle remains the existing transactional lifecycle.

Same-object rules, shared controllers and standalone jobs use this path before any Results read. A metadata-only interface patch that produces no value pairs does not initiate conditional reconciliation; this preserves the existing provenance-only behavior.

3 · Replace a relationship

The second local diagnostic confirms that assigning a ByteDance API to a 1080p job succeeds today. The normalized modeling-object replacement is absent from the current explainable-value membership loop. Each relationship segment must be a trigger, so a job's API replacement validates its resolution even without an API model edit.

dependent_inputs() looks up the changed owner type/input in the trigger index, then follows only that entry's ordered reverse hops through contextual_modeling_obj_containers. Filter each ContextualModelingObjectAttribute by live owner, expected relationship attribute and owner type before reading that owner's input. Confirm the wrapper is still the value at that direct input address. Detached wrappers, list/dict links and calculated references cannot satisfy a direct path.

[PLAN-UPDATE-02] — PROPOSED

The library rejects incompatible batches; the interface chooses first-option corrections. Extend object_factory.py with the shared repair helper and result instead of introducing the kickoff's provisional service module. The helper prepares candidates, reconciles through library queries, and performs one library transaction. Each application use case remains responsible for its final persistence call.

model_builder/domain/object_factory.py Proposed contract; illustrative Python

@dataclass
class AutomaticInputChange:
    input: InputRef
    previous_value: ExplainableObject
    accepted_value: ExplainableObject

@dataclass
class InputEditResult:
    automatic_changes: list[AutomaticInputChange]
    affected_inputs: set[InputRef]  # includes retained values with changed options

apply_input_edits(parsed_data: dict, owner: ModelingObjectWeb) -> InputEditResult
# All explicit fields enter before any generated correction.
# No persistence in this helper.

Prepare, reconcile, apply

  1. Collect all explicit value-bearing fields in the submitted edit, including unchanged submitted values. Metadata-only payloads are not explicit value choices. Share the existing source inventory and pending-source dictionary across all owners. Prepare replacement pairs and seed the complete candidate map before querying dependencies.
  2. Find the reachable conditional inputs using dependent_inputs(), following downstream inputs to cover supported chains. Process controlling inputs before their dependents using the resolved candidate relationships, so a generated Model correction is considered before job Resolutions. This is ordering of the affected dependency graph, not a general constraint solver.
  3. Call allowed_values() for each affected input's final options. Keep a valid value; reject a conflicting explicit submission or an empty branch. Otherwise choose the first allowed option and run its value through the existing preparer after omitting option provenance. The owner's existing label/source/confidence/comment survive; returned option constants are never attached directly.
  4. Collect generated replacements by input address, replacing a staged candidate rather than producing multiple old-value pairs for the same input. Record one notice per automatic replacement and include retained dependents when their options change.
  5. Submit all final pairs to one ModelingUpdate. Convert a library choice failure to the existing InputValidationError for normal error presentation. Return the structured result only after success.

For the normal API form, Provider and Model are explicit submissions, while linked job Resolutions are not. An incompatible explicit Model is rejected; jobs needing a compatible Resolution are repaired. Direct Python callers can explicitly submit compatible changes across owners through the library batch API.

Normal integration and persistence

EditObjectUseCase.execute() retains the existing ServerWeb.pre_edit() and EdgeComputerWeb.pre_edit() calls. They edit request-local nested storage before the main owner, with no persistence. None of today's conditional declarations spans those submissions, so do not rewrite the composite workflow. The main owner's submitted fields and every generated conditional correction still reach one transaction together.

Carry the shared result through edit_object_from_parsed_data(), EditResult and EditObjectOutput. Cascade cleanup still runs after successful application. Name changes and same-value metadata patches stay request-local until the whole edit succeeds; the existing request-discard policy covers rejection without a separate metadata rollback store.

Normal edits retain persist_structural_change() as their single final model/config save. Simplified edits retain selection/eligibility checks and their single persist_to_cache() call. Rejected edits call neither final save and publish no inputs, relationships, provenance or Results. This relies on the existing request-local persistence boundary.

Feedback follows the accepted state

Both use cases turn automatic-change records into notices naming the owner, existing input label and accepted value. Map library input references to the existing FieldAddress at the interface boundary. Simplified rendering continues to use present_edited_input() to replace affected visible fields and refresh Results controls.

Add notices to normal edit output and its present_edited_object() response. Extend the existing normal edit toast handler to append those messages as text alongside ordinary save/constraint feedback. Refresh cards of repaired owners through the presenter's existing top-parent/mirror rendering, deduplicating cards already covered by a canvas OOB region. Normal Save closes its editor; there is no retained job editor to synchronize in the background. Reopening it obtains the accepted value and choices through the shared generator.

Keep existing recomputation triggers and rejection modals; no new recovery surface or browser mutation protocol is needed. See Rendering and mutation feedback for the owning response pattern.
