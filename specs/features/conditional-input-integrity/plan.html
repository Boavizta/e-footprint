Plan — approved · 2026-10-13

Conditional input integrity

Feature spec · Proposed changed files

Add a reverse lookup for the existing conditional declarations. Library updates use it to check affected inputs after applying a batch; normal and simplified editors use it to prepare compatible corrections before saving.

Library paths are relative to e-footprint; interface paths are relative to e-footprint-interface. Source links show existing code. File-labelled snippets show proposed changes; application implementation and task preparation remain separate stages.

Small glossary

Hover over or focus dotted terms to see their definitions.

Controlling input
An input whose value determines the allowed choices for another input.
Dependent input
An input whose allowed choices depend on another input, such as a job’s resolution.
Referring object
An object whose field points to another object, such as a job using an API.
Input owner
The object containing an input: the job is the owner of its resolution.
Input address
An object and field name identifying one input, such as (job, resolution).
Trigger index
The dictionary saying which dependent inputs to check when an input changes.
Reverse hop
One step backward along a reference, such as going from an API to a job using it.
Backlink
Stored information identifying objects that point to an object.
Conditional branch
The allowed choices associated with one controlling value, such as resolutions for one AI model.
Proposed changes
Values or relationships staged separately until the edit is applied.
Wrapper
A small object holding a reference and information about where that reference is used.

1 · Trigger index

conditional_list_values remains the authoritative dependency and choice mapping. The new efootprint/abstract_modeling_classes/conditional_inputs.py holds a private module-level _trigger_index dictionary so a controller change can find inputs declared on referring objects. Job and API below are shortened video class names.

efootprint/abstract_modeling_classes/conditional_inputs.py Example dictionary after the video-job class is registered

_trigger_index = {
    (API, "model_name"): [
        {
            "dependent_type": Job,
            "dependent_attribute": "resolution",
            "reverse_hops": ((Job, "external_api"),),
        },
    ],
    (Job, "external_api"): [
        {
            "dependent_type": Job,
            "dependent_attribute": "resolution",
            "reverse_hops": (),
        },
    ],
}

A key names the changed owner type and input. Each entry names a dependent input and the reverse relationship hops needed to reach its owner:

  • An API model-name edit starts at the API, finds jobs referring to it through their API relationship, then checks their resolutions.
  • A job's API replacement starts at the job itself. The empty reverse-hop tuple means check that job's resolution directly.

The entries are derived from the job's declaration and constructor annotation. Branch choices stay in cls.conditional_list_values; the index stores classes, attribute names and routing information, with no model instances or persisted state.

efootprint/abstract_modeling_classes/conditional_inputs.py Existing metadata read during registration

Job.conditional_list_values["resolution"]["depends_on"]
# -> "external_api.model_name"

get_init_signature_params(Job)["external_api"].annotation
# -> API

[PLAN-UPDATE-01] — ACCEPTED

Add ModelingObject.__init_subclass__() in efootprint/abstract_modeling_classes/modeling_object.py. It calls register_conditional_inputs(cls) in conditional_inputs.py when Python defines each subclass, normally during module import:

efootprint/abstract_modeling_classes/modeling_object.py Proposed changes; illustrative Python

class ModelingObject(metaclass=ABCAfterInitMeta):
    def __init_subclass__(cls, **kwargs):
        super().__init_subclass__(**kwargs)
        from efootprint.abstract_modeling_classes.conditional_inputs import register_conditional_inputs
        register_conditional_inputs(cls)

register_conditional_inputs(cls) iterates cls.conditional_list_values, resolves the relationship types with get_init_signature_params(), verifies each path and adds entries for its final controlling input and each replaceable relationship segment. A class without declarations adds no entries. Current annotations follow the existing constructor convention against forward references.

Read inherited declarations from the effective subclass. Registration reports an unknown relationship or final input with the class and full path. An annotation admitting several modeling-object types produces the corresponding routes; paths through lists or dictionaries remain outside the feature.

Later class definitions extend the dictionary directly. Runtime lookup walks the changed owner's class hierarchy and reads matching keys; it needs no separate controller lookup. Construction uses the registered index for local validation; hydration leaves membership checks disabled, and _mark_live() retains its existing instance-lifecycle responsibility.

2 · Change a library input

A normal Python assignment reaches ModelingObject.__setattr__(), which starts ModelingUpdate; callers can also submit an explicit batch. Today the update checks only new_sourcevalues. The reproduced API-model edit therefore accepts an unchanged job resolution that the new model does not support.

Keep parse_changes_list() for type/unit checks, normalization, entangled changes and no-op detection. Capture each changed input as an ordinary tuple of actual owner and attribute name before its old value detaches. After the existing apply/invalidation step, extend the set checked inside the rollback boundary:

efootprint/abstract_modeling_classes/modeling_update.py Proposed extension of the existing live-update validation loop

# Capture addresses after normalization, before applying replacements.
changed_inputs = {
    (old.modeling_obj_container, old.attr_name_in_mod_obj_container)
    for old, new in self.changes_list
}

# After the existing complete apply/invalidation step:
try:
    affected_inputs = changed_inputs | dependent_inputs(changed_inputs)
    for owner, attribute in affected_inputs:
        owner.check_belonging_to_authorized_values(attribute)
    self.pull_eagerly(visited_slots)
except Exception:
    self.rollback()
    raise

This is the first consumer of dependent_inputs(), implemented in conditional_inputs.py. It takes the changed tuple addresses and uses _trigger_index to return the next affected conditional inputs. For an API shared by two video jobs:

efootprint/abstract_modeling_classes/conditional_inputs.py Proposed changes; illustrative Python

dependent_inputs({(api, "model_name")})
# -> {(job_a, "resolution"), (job_b, "resolution")}

# Inside dependent_inputs():
for owner_type in type(changed_owner).__mro__:
    entries = _trigger_index.get((owner_type, changed_attribute), ())
    # Follow each entry's reverse_hops to the dependent owner.

dependent_inputs() returns all affected input addresses, including inputs whose current value remains allowed. Their available options may have changed even when their value needs no replacement. It follows one conditional dependency at a time, even when that dependency traverses several object relationships. Match referring owners by the named relationship and its declared type; a reached dependent must have the exact class recorded in its entry, so an overridden subclass declaration is not discovered through its parent's old path. Deduplicate returned addresses and stop at the dependent owner.

Reuse the existing membership check

check_belonging_to_authorized_values() checks one named input with an optional proposed_changes mapping. It reads that input and its controller from the mapping when present, or from the attached object otherwise. Remove its existing value and same-object dependent-map arguments, and remove attributes_with_depending_values(). The caller discovers affected inputs through dependent_inputs(); the validator does not recursively discover or validate other inputs. Ordinary type, positivity and unit validation stay at their current boundaries.

[PLAN-UPDATE-04] — ACCEPTED

The existing attributes_with_depending_values() duplicates the local part of the new dependent_inputs() lookup. Remove it and simplify check_belonging_to_authorized_values() to one name and an optional proposed-changes mapping. During _set_input_passively(), discover all already attached dependents with proposed-state lookup before attaching the new value, including dependents on referring objects. This preserves constructor-time rejection without a second reverse map; JSON hydration still bypasses input validation as it does today. No spec capability changes.

During construction, _set_input_passively() checks each assignment before attachment. Supply the proposed value as a map of proposed changes with one entry, validate the assigned input, then use dependent_inputs() to find already assigned dependents on any reached owner. Validate those dependents against the proposed state and skip fields not yet assigned. A dependent assigned before its required controller still fails when its controller path cannot be resolved. This also covers replacing a relationship on the constructing object after its dependent was assigned. Hydration keeps its existing explicit validation bypass.

efootprint/abstract_modeling_classes/modeling_object.py Proposed constructor-time check; illustrative Python

proposed_changes = {(self, name): input_value}
self.check_belonging_to_authorized_values(name, proposed_changes)
for owner, attribute in dependent_inputs({(self, name)}, proposed_changes):
    if attribute in owner.__dict__:  # Skip inputs not yet assigned.
        owner.check_belonging_to_authorized_values(attribute, proposed_changes)
# Attach input_value only after these checks succeed.

For a conditional input, the validator reads its declaration directly and resolves the controlling input. Move the existing interface resolve_input_path() into conditional_inputs.py. Keep its simple tuple return and wrapped-owner normalization:

efootprint/abstract_modeling_classes/modeling_object.py Proposed changes; illustrative Python

# Inside check_belonging_to_authorized_values(name, proposed_changes=None):
proposed_changes = proposed_changes or {}
address = (self, name)
input_value = (proposed_changes[address] if address in proposed_changes
               else getattr(self, name))
declaration = self.conditional_list_values[name]
controller_owner, controller_attribute = resolve_input_path(
    self, declaration["depends_on"], proposed_changes
)
controller_address = (controller_owner, controller_attribute)
controller_value = (proposed_changes[controller_address] if controller_address in proposed_changes
                    else getattr(controller_owner, controller_attribute))
options = allowed_values(type(self), name, controller_value)
# Compare the submitted value with options using input_values_match().

resolve_input_path() follows the declared relationship names and returns the actual owner and final attribute. A missing relationship or input reports the complete path, because the controlling value cannot be obtained.

The single allowed_values() helper, also in conditional_inputs.py, takes the dependent class, attribute name and already-known controller value. It extracts the branch-selection logic from check_belonging_to_authorized_values() and reads the class's static and conditional lists directly. Both controller-key matching and allowed-value comparisons use input_values_match().

Declaration for the controlling valueResult used by validation
A branch lists choicesThose choices in declared order, filtered by any static-list restriction.
No branch is declaredThe static list if present; otherwise None, meaning unrestricted by these choice lists.
An explicitly empty branch is declaredAn empty tuple: no value is permitted.

For a static-only input, pass None as the controller value; the same helper returns its static choices. Option objects remain metadata values; validation reads them. A missing branch does not relax type/unit checks, and absence remains distinct from explicit zero.

Only after membership succeeds does pull_eagerly() run the existing guards and configured outputs. On failure, rollback() restores inputs and relationships and re-invalidates/re-pulls that eager boundary. Other caches may remain void and recompute on read, following the existing update lifecycle.

The error names the affected object/input, unsupported value, controlling object/input and value, and permitted choices; an empty branch states that no compatible choice exists. A controller-only incompatible edit rejects, while a batch containing all necessary corrections accepts in either submission order. The lookup uses declared relationships and works on standalone or cold objects, without calculation-history dependence.

3 · Replace a relationship

Assigning a new API to a job enters the same update path. After the entire batch attaches, dependent_inputs() sees the changed job/API address and returns that job's resolution using the second index entry in the opening example. check_belonging_to_authorized_values() then checks it against the new API's model.

For a reverse hop, dependent_inputs() reads contextual_modeling_obj_containers and filters each ContextualModelingObjectAttribute by its live owner, named relationship and expected type. Confirm the wrapper is still stored at that direct input address. Detached wrappers and list/dict/calculated relationships cannot satisfy a direct path.

The same lookup handles a longer relationship path

A synthetic job's choice can depend on a bridge's API model. Its index contains an entry for replacing either relationship as well as for changing the terminal model:

efootprint/abstract_modeling_classes/conditional_inputs.py Proposed dictionary for a synthetic multi-hop declaration

# SyntheticJob declares depends_on = "bridge.api.model_name".
# Annotations: SyntheticJob.bridge: Bridge; Bridge.api: API.
_trigger_index = {
    (API, "model_name"): [
        {"dependent_type": SyntheticJob, "dependent_attribute": "choice",
         "reverse_hops": ((Bridge, "api"), (SyntheticJob, "bridge"))},
    ],
    (Bridge, "api"): [
        {"dependent_type": SyntheticJob, "dependent_attribute": "choice",
         "reverse_hops": ((SyntheticJob, "bridge"),)},
    ],
    (SyntheticJob, "bridge"): [
        {"dependent_type": SyntheticJob, "dependent_attribute": "choice",
         "reverse_hops": ()},
    ],
}

An API edit reverses both hops; a bridge's API replacement reverses only the job/bridge hop; replacing the job's bridge checks the job directly. Each route stops at the dependent owner.

Accepted replacements become the links followed by later validation. Changes to the old API no longer check redirected jobs; changes to the new API do. Rejected replacements restore the previous links. Preserve collect_newly_linked_mod_objs() and its existing guard behavior for new links.

Conditional discovery visits only matching reverse paths and affected input addresses. It must not read unrelated owners' inputs, pull computed getters or continue toward a System. Every job sharing a changed API is still checked. See the existing relationship representation.

No new job-redirection control is added to the interface. Staging a proposed relationship for repair or option discovery uses the map of proposed changes introduced in the next save flow.

6 · Upgrade older files to version 26

[PLAN-UPDATE-03] — ACCEPTED

Ship library version 26.0.0 with a narrow 25→26 correction for incompatible historical video-job resolutions. Live validity is enforced in ModelingUpdate; generic import revalidation, footprint-time validation and special recovery UI remain outside the feature.

An older snapshot reaches upgrade_system_dict_to_current_version(). Add a handler at key 25 in VERSION_UPGRADE_HANDLERS, and advance efootprint/version.py and pyproject.toml to 26.0.0.

efootprint/api_utils/version_upgrade_handlers.py Proposed version handler; operates on serialized inputs

upgrade_version_25_to_26(system_dict, efootprint_classes_dict=None):
    for each saved EcoLogitsVideoGenExternalAPIJob:
        resolve its external_api ID to the saved video API
        read the saved model_name as a source value
        options = allowed_values(job_class, "resolution", saved_model)
        if options and saved_resolution does not match any option:
            resolution = job_payload["resolution"]
            note = replacement note from old value, controller and old source metadata
            resolution["value"] = options[0].value
            resolution["source"] = Sources.AUTOMATIC_REPLACEMENT.id
            resolution.pop("confidence", None)
            resolution["comment"] = note
            system_dict.setdefault("Sources", {})[
                Sources.AUTOMATIC_REPLACEMENT.id
            ] = Sources.AUTOMATIC_REPLACEMENT.to_json()
    return system_dict

The handler knows the controller value, so it calls allowed_values() directly using the supplied class registry or existing API-layer fallback. It reads the existing video-job metadata rather than hydrating a temporary graph. Iterate the serialized job collection so disconnected jobs are included.

Change only an unsupported resolution with an available compatible option. Read the old source label and optional link from the snapshot's existing Sources block before changing its reference. Keep the resolution label, record the old source, confidence and comment in the replacement note, then set the automatic-replacement source ID, clear confidence and insert that source's payload into the existing Sources block. Create the block when absent; its shape stays unchanged. Preserve relationships and all other authored inputs. Missing or empty branches offer no replacement and leave the saved input unchanged. This handler does not repair provider/model pairs or malformed files.

json_to_system() already uses the original file version to reject old computed caches, keeping eligible values as a historical comparison baseline. Fresh calculations consume the corrected inputs under the existing version-aware load contract. Current-version files do not rerun the migration, and the snapshot structure stays unchanged.

The interface currently uses an editable library dependency. Preserve existing dependency and lockfile edits during local validation; deliberately restore a publishable version-26 requirement and update its lock before coordinated changes reach main. Publication and deployment remain separate actions.
