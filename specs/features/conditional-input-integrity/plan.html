Approved plan · implementation review guide

Conditional input integrity

Feature spec · Implementation review files

The implementation adds a reverse lookup for the existing conditional declarations. Library updates use it to check affected inputs after applying a batch; normal and simplified editors use it to prepare compatible corrections before saving.

Library paths are relative to e-footprint; interface paths are relative to e-footprint-interface. Source links identify delivered code. Snippets are abridged implementation shapes or explicitly labelled illustrative payloads.

Small glossary

Hover over or focus dotted terms to see their definitions.

Controlling input
An input whose value determines the allowed choices for another input.
Dependent input
An input whose allowed choices depend on another input, such as a job’s resolution.
Referring object
An object whose field points to another object, such as a job using an API.
Input owner
The object containing an input: the job is the owner of its resolution.
Input address
An object and field name identifying one input, such as (job, resolution).
Trigger index
The dictionary saying which dependent inputs to check when an input changes.
Reverse hop
One step backward along a reference, such as going from an API to a job using it.
Backlink
Stored information identifying objects that point to an object.
Conditional branch
The allowed choices associated with one controlling value, such as resolutions for one AI model.
Proposed changes
Values or relationships staged separately until the edit is applied.
Wrapper
A small object holding a reference and information about where that reference is used.

1 · Trigger index

Implemented as planned. The module records effective class declarations at subclass definition and exposes the shared lookup and choice queries.

conditional_list_values remains the authoritative dependency and choice mapping. The new efootprint/abstract_modeling_classes/conditional_inputs.py holds the private module-level _trigger_index dictionary so a controller change can find inputs declared on referring objects. Job and API below are shortened video class names.

efootprint/abstract_modeling_classes/conditional_inputs.py Illustrative _Trigger entries after the video-job class is registered

_trigger_index = {
    (API, "model_name"): [
        _Trigger(Job, "resolution", ((Job, "external_api"),)),
    ],
    (Job, "external_api"): [
        _Trigger(Job, "resolution", ()),
    ],
}

Each key names the changed owner type and input. Each entry names a dependent input and the reverse relationship hops needed to reach its owner:

  • An API model-name edit starts at the API, finds jobs referring to it through their API relationship, then checks their resolutions.
  • A job's API replacement starts at the job itself. The empty reverse-hop tuple means check that job's resolution directly.

The entries are compact _Trigger records derived from the job's declaration and its constructor relationship annotation. Branch choices stay in cls.conditional_list_values; the index stores classes, attribute names and routing information, with no model instances or persisted state.

efootprint/abstract_modeling_classes/conditional_inputs.py Existing metadata read during registration

Job.conditional_list_values["resolution"]["depends_on"]
# -> "external_api.model_name"

get_init_signature_params(Job)["external_api"].annotation
# -> API

[PLAN-UPDATE-01] — ACCEPTED

Added ModelingObject.__init_subclass__() in efootprint/abstract_modeling_classes/modeling_object.py. It calls register_conditional_inputs(cls) in conditional_inputs.py when Python defines each subclass, normally during module import:

efootprint/abstract_modeling_classes/modeling_object.py Abridged implemented registration hook

class ModelingObject(metaclass=ABCAfterInitMeta):
    def __init_subclass__(cls, **kwargs):
        super().__init_subclass__(**kwargs)
        from efootprint.abstract_modeling_classes.conditional_inputs import register_conditional_inputs
        register_conditional_inputs(cls)

register_conditional_inputs(cls) iterates cls.conditional_list_values, resolves the relationship types with get_init_signature_params(), verifies each path and adds _Trigger records for its final controlling input and each replaceable relationship segment. A class without declarations adds no entries. Current annotations follow the existing constructor convention against forward references.

Read inherited declarations from the effective subclass. Registration reports an unknown relationship or final input with the class and full path. An annotation admitting several modeling-object types produces the corresponding routes; paths through lists or dictionaries remain outside the feature.

Later class definitions extend the dictionary directly. Runtime lookup walks the changed owner's class hierarchy and reads matching keys; it needs no separate controller lookup. Construction uses the registered index for local validation; hydration leaves membership checks disabled, and _mark_live() retains its existing instance-lifecycle responsibility.

2 · Change a library input

Implemented as planned, with IMPL-DECISION-01. Constructors check staged assignments; live updates validate the complete applied batch inside rollback.

A normal Python assignment reaches ModelingObject.__setattr__(), which starts ModelingUpdate; callers can also submit an explicit batch. Before Run A, the update checked only new_sourcevalues. The reproduced API-model edit therefore accepted an unchanged job resolution that the new model did not support.

The update retains parse_changes_list() for type/unit checks, normalization, entangled changes and no-op detection. It captures each changed input as an ordinary tuple of actual owner and attribute name before the old value detaches. After the batch is applied and invalidated, it validates the changed and dependent addresses inside the rollback boundary:

efootprint/abstract_modeling_classes/modeling_update.py Abridged implemented live-update validation loop

# Capture addresses after normalization, before applying replacements.
changed_inputs = {
    (old.modeling_obj_container, old.attr_name_in_mod_obj_container)
    for old, new in self.changes_list
}

# After the existing complete apply/invalidation step:
try:
    affected_inputs = changed_inputs | dependent_inputs(changed_inputs)
    for owner, attribute in affected_inputs:
        owner.check_belonging_to_authorized_values(attribute)
    self.pull_eagerly(visited_slots)
except Exception:
    self.rollback()
    raise

This is the first consumer of dependent_inputs() in the new module. It takes the changed tuple addresses and uses _trigger_index to return the next affected conditional inputs. For an API shared by two video jobs:

dependent_inputs({(api, "model_name")})
# -> {(job_a, "resolution"), (job_b, "resolution")}

# Inside dependent_inputs():
for owner_type in type(changed_owner).__mro__:
    entries = _trigger_index.get((owner_type, changed_attribute), ())
    # Follow each entry's reverse_hops to the dependent owner.

dependent_inputs() returns all affected input addresses, including inputs whose current value remains allowed. Their available options may have changed even when their value needs no replacement. It follows one conditional dependency at a time, even when that dependency traverses several object relationships. Match referring owners by the named relationship and its declared type; a reached dependent must have the exact class recorded in its entry, so an overridden subclass declaration is not discovered through its parent's old path. Deduplicate returned addresses and stop at the dependent owner.

Reuse the existing membership check

check_belonging_to_authorized_values() checks one named input with an optional proposed_changes mapping. It reads that input and its controller from the mapping when present, or from the attached object otherwise. The validator no longer accepts its former value and same-object dependent-map arguments; its caller discovers affected inputs through dependent_inputs(). It does not recursively discover or validate other inputs. Ordinary type, positivity and unit validation remain at their existing boundaries.

[PLAN-UPDATE-04] — ACCEPTED

Run A replaced the old local reverse lookup with dependent_inputs(), and simplified check_belonging_to_authorized_values() to one name and an optional proposed-changes mapping. During _set_input_passively(), the new lookup discovers already attached dependents before the value attaches, including dependents on referring objects. This preserves constructor-time rejection without a second reverse map; JSON hydration still bypasses input validation. No spec capability changed.

During construction, _set_input_passively() stages each assignment as a one-entry proposed-change map, validates that input, then uses dependent_inputs() to find already assigned dependents on reached owners. It validates those dependents against the staged state and skips fields not yet assigned. A dependent assigned before its required controller still fails when its controller path cannot be resolved. This also covers replacing a relationship on the constructing object after its dependent was assigned. Hydration keeps its explicit validation bypass.

[IMPL-DECISION-01] — APPLIED

Run A, Task 2 exposed a pre-existing failed-constructor backlink leak. A job could attach its API, then fail validation of a later input; the failed job remained in the API's reverse links, and a subsequent valid API edit reached its missing input and failed. This is a defense-in-depth library invariant: no current production path in the library or interface catches that construction error and then reuses the same in-memory graph, and the failed object is not persisted by the interface. The approved per-input check alone did not release relationships attached by earlier constructor assignments. The regression is captured in test_failed_constructor_detaches_relationships_before_later_controller_edits().

AfterInitMeta.__call__() now retains the partially built instance through initialization, drops its cached slot values and dependency edges, detaches attached relationship values, and re-raises the original error. This adds failure cleanup to the construction lifecycle; the maintenance cost is an explicit metaclass construction path and cleanup of both relationships and computed state. Normal successful initialization is unchanged. The later controller edit no longer sees the failed object, while the original constructor error remains visible; test_failed_after_init_detaches_cached_values_and_preserves_original_error() covers cleanup after a failing post-init hook.

efootprint/abstract_modeling_classes/modeling_object.py Abridged implemented constructor-time check

proposed_changes = {(self, name): input_value}
self.check_belonging_to_authorized_values(name, proposed_changes)
for owner, attribute in dependent_inputs({(self, name)}, proposed_changes):
    if attribute in owner.__dict__:  # Skip inputs not yet assigned.
        owner.check_belonging_to_authorized_values(attribute, proposed_changes)
# Attach input_value only after these checks succeed.

For a conditional input, the validator reads its declaration directly and resolves the controlling input. The former interface resolve_input_path() now lives in the library. resolve_input_path() returns the controller owner and attribute, and normalizes wrapped owners: wrapped-owner normalization:

efootprint/abstract_modeling_classes/modeling_object.py Abridged implemented membership check

declaration = type(self).conditional_list_values.get(name)
if declaration is None and name not in type(self).list_values:
    return
address = (self, name)
input_value = proposed_changes[address] if address in proposed_changes else self.__dict__[name]
controller_value = None
if declaration is not None:
    owner, attribute = resolve_input_path(self, declaration["depends_on"], proposed_changes)
    controller = (owner, attribute)
    controller_value = proposed_changes[controller] if controller in proposed_changes else owner.__dict__[attribute]
options = allowed_values(type(self), name, controller_value)
if options is not None and not any(input_values_match(input_value, allowed) for allowed in options):
    raise ValueError(...)

resolve_input_path() follows the declared relationship names and returns the actual owner and final attribute. A missing relationship or input reports the complete path, because the controlling value cannot be obtained.

The single allowed_values() helper takes the dependent class, attribute name and already-known controller value. It extracts the branch-selection logic from check_belonging_to_authorized_values() and reads the class's static and conditional lists directly. Both controller-key matching and allowed-value comparisons use input_values_match().

Declaration for the controlling valueResult used by validation
A branch lists choicesThose choices in declared order, filtered by any static-list restriction.
No branch is declaredThe static list if present; otherwise None, meaning unrestricted by these choice lists.
An explicitly empty branch is declaredAn empty tuple: no value is permitted.

For a static-only input, pass None as the controller value; the same helper returns its static choices. Option objects remain metadata values; validation reads them. A missing branch does not relax type/unit checks, and absence remains distinct from explicit zero.

Only after membership succeeds does pull_eagerly() run the existing guards and configured outputs. On failure, rollback() restores inputs and relationships and re-invalidates/re-pulls that eager boundary. Other caches may remain void and recompute on read, following the existing update lifecycle.

The error names the affected object/input, unsupported value, controlling object/input and value, and permitted choices; an empty branch states that no compatible choice exists. A controller-only incompatible edit rejects, while a batch containing all necessary corrections accepts in either submission order. The lookup uses declared relationships and works on standalone or cold objects, without calculation-history dependence.

3 · Replace a relationship

Implemented as planned. Proposed links participate in lookup without attaching them; accepted live replacements become the links used by later validation.

Assigning a new API to a job enters the same update path. After the entire batch attaches, dependent_inputs() sees the changed job/API address and returns that job's resolution using the second index entry in the opening example. check_belonging_to_authorized_values() then checks it against the new API's model.

For a reverse hop, dependent_inputs() reads contextual_modeling_obj_containers and filters each ContextualModelingObjectAttribute by its live owner, named relationship and expected type. Confirm the wrapper is still stored at that direct input address. Detached wrappers and list/dict/calculated relationships cannot satisfy a direct path.

The same lookup handles a longer relationship path

A synthetic job's choice can depend on a bridge's API model. Its index contains an entry for replacing either relationship as well as for changing the terminal model:

efootprint/abstract_modeling_classes/conditional_inputs.py Illustrative multi-hop _Trigger entries

# SyntheticJob declares depends_on = "bridge.api.model_name".
# Annotations: SyntheticJob.bridge: Bridge; Bridge.api: API.
_trigger_index = {
    (API, "model_name"): [
        _Trigger(SyntheticJob, "choice", ((Bridge, "api"), (SyntheticJob, "bridge"))),
    ],
    (Bridge, "api"): [
        _Trigger(SyntheticJob, "choice", ((SyntheticJob, "bridge"),)),
    ],
    (SyntheticJob, "bridge"): [
        _Trigger(SyntheticJob, "choice", ()),
    ],
}

An API edit reverses both hops; a bridge's API replacement reverses only the job/bridge hop; replacing the job's bridge checks the job directly. Each route stops at the dependent owner.

Accepted replacements are the links followed by later validation. Changes to the old API no longer check redirected jobs; changes to the new API do. Rejected replacements restore the previous links. collect_newly_linked_mod_objs() retains its guard behavior for new links.

Conditional discovery visits only matching reverse paths and affected input addresses. It must not read unrelated owners' inputs, pull computed getters or continue toward a System. Every job sharing a changed API is still checked. See the existing relationship representation.

No new job-redirection control is added to the interface. Staging a proposed relationship for repair or option discovery uses the map of proposed changes introduced in the next save flow.

4 · Save in either editor

Implemented as planned, with IMPL-DECISION-02. Both editors share staged repair and provenance; notices travel in the response body.

Before Run A, Normal Save flowed through EditObjectUseCase.execute(), then EditService.edit_with_cascade_cleanup(), then edit_object_from_parsed_data(). The Simplified flow already gathered repairs across owners.

Both flows call apply_input_edits() in model_builder/domain/object_factory.py. The former Simplified repair loop was extracted beside prepare_input_changes(). The library remains responsible for rejection, the interface chooses replacements, and each owning use case controls persistence.

Prepare the user's submitted values

apply_input_edits() passes submitted fields through prepare_input_changes(), sharing source lookup and pending sources across generated owner edits. It tracks explicit value-bearing fields even when their values are unchanged; metadata-only fields do not count as explicit choices. It seeds a proposed-changes map using the same ordinary owner/attribute tuples as the library update:

Repair affected choices before applying the batch

Starting from those addresses, dependent_inputs() finds required companions; the factory repeats discovery from reached inputs to cover chains. It evaluates controllers before dependents using the proposed relationships and choice helper linked above. A Provider change can therefore lead to a Model correction before job resolutions are evaluated. Normal forms submit both Provider and Model explicitly, so an incompatible submitted Model rejects while linked job resolutions can be repaired.

This abridged factory excerpt shows how one reached input is evaluated. The existing metadata tells the factory which controller to read; the same resolver and choice helper used by the library validator operate on the prepared values:

The proposed_changes argument on resolve_input_path() and dependent_inputs() supports proposed-state reads without mutating the live graph. The resolver follows proposed relationship replacements at each hop. Reverse discovery skips live links overridden by a proposed change and includes the proposed links instead; the trigger index remains class-level routing data.

[PLAN-UPDATE-05] — ACCEPTED

The revised provenance requirement replaced the earlier plan to copy the dependent value's metadata unchanged onto an automatic correction. The review recorded that the normal preparer retained prior metadata while the original Simplified repair omitted option metadata. Run A resolves that mismatch in apply_input_edits(): generated replacements receive the stable Sources.AUTOMATIC_REPLACEMENT source, clear confidence and prepend a comment note. The note records old and new values, the controller change for an editor repair or unsupported saved model for migration, the previous source label and link when present, previous confidence, and the previous comment text verbatim. prepare_input_changes() preserves the field label. The 25→26 migration applies the same policy; compatible values retain their metadata.

The library defines Sources.AUTOMATIC_REPLACEMENT with stable ID automatic_replacement and display name “automatic replacement”. The loader maps that ID through _resolve_sentinel_source() and build_sources_dict_from_system_dict(), so editor saves and upgrades reload with the canonical source. Existing source serialization includes sources referenced by inputs; no new snapshot field is needed.

In apply_input_edits(), prepare_input_changes() preserves the dependent field's label. The repair helper sets its source, clears confidence and prepends the new note to prior comment history; absent prior source or confidence is recorded as “none”. The note and source persist with the accepted batch. A rejected edit leaves the original value and metadata untouched. The 2,000-character cap was removed from source_editor.html so repeated notes and the previous comment remain editable.

The same source editor receives referenced sources as choices. It shows “automatic replacement” when it is the current source, but does not offer it as a new manual selection for another field. The stored source and comment remain visible after reopening.

Apply once, then save and explain the repairs

apply_input_edits() submits the controller and generated dependent corrections to one ModelingUpdate. The factory translates membership errors to InputValidationError for existing editor error presentation. The shared result records automatic replacements and affected addresses, including retained values whose options changed:

[IMPL-DECISION-02] — APPLIED

Run A, Task 5 added a response-body notice path because the approved normal-edit feedback would have placed one message per repaired job in an unbounded HTMX settle header. A real accepted 200-job batch produced an 11,803-byte trigger header, exposing the project's known nginx header-overflow risk. The existing Simplified save path had the same unbounded notice-header defect. The previous feedback paths were HtmxPresenter.present_edited_object() and present_edited_input(); the large-batch regression is test_large_accepted_repair_batch_carries_every_notice_in_body_with_bounded_headers().

Both presenters render every escaped notice through the shared input_repair_notices.html fragment into the stable hidden target in toast.html. The settle header carries only a fixed target ID; the normal displayToastAndHighlightObjects handler and Simplified simplifiedInputSaved handler read its text after the OOB swap. This preserves all notices and their existing separators and timing. The maintenance cost is a shared presenter/template/DOM contract that both editors must keep in sync; the response header size no longer grows with job count.

5 · Configure and render choices

Implemented as planned. Both form consumers query the library rules for current and cascade choices.

build_catalog() and generate_dynamic_form() use the library resolve_input_path() with the library version introduced above. The duplicate model_builder/domain/conditional_inputs.py has been removed.

In generate_dynamic_form(), the implementation uses a local choices_for() adapter that calls allowed_values(): once for the current controller when opening an editor, once per controller choice for a same-object browser cascade, and once per referenced object for a dotted cascade.
