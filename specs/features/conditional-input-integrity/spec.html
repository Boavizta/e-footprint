Conditional input integrity

Status: Spec — under review · 2026-10-12

Library-driven feature spanning e-footprint and e-footprint-interface. Draft plan from the kickoff discussion.

1. Problem and audience

A valid input can become invalid when another input changes. For example, changing a video API's AI model can invalidate the resolutions of jobs using that API. Redirecting a job to a different API can produce the same problem.

Today, normal editing can save that incompatible combination. Reopening the job editor shows a supported resolution even though a different, unsupported resolution remains stored. Results can calculate successfully from that unsupported combination, so neither apparent correction nor successful computation proves that the modeling is valid.

Simplified inputs already repairs dependent choices across objects. Normal editing and direct library changes do not have equivalent protection. The interface also interprets dependency rules independently in several places, increasing the risk of inconsistent behavior.

This affects model authors changing providers or AI models, colleagues adapting a modeling through Simplified inputs, and Python callers changing inputs or object relationships. The immediate risk is silently calculating an environmental footprint for an unsupported combination.

2. Success criteria

  1. Valid state after every accepted change. A library change that would leave an affected conditional input invalid fails with an actionable error identifying the affected object/input and constraint. The previous inputs, relationships and computed state remain coherent.
  2. Both sources of invalidation are covered. Protection applies when a controlling value changes and when any object relationship along its dependency path is replaced. It covers shared controllers, dependency chains and paths through several related objects.
  3. Whole-batch validation. A caller can submit a controller and all necessary dependent corrections together. Acceptance depends on the final combination, independent of submission order; no valid batch is rejected for an intermediate state.
  4. Consistent editor repair. Normal and simplified edits retain dependent values that remain valid. Otherwise they choose the first allowed option in the declared order and explain each automatic change. Controller and dependent changes save together. A branch with no allowed choice rejects the complete edit.
  5. Explicit choices remain explicit. A conflicting dependent value expressly submitted by the caller is rejected rather than silently overwritten. Automatic replacements preserve the dependent input's label and provenance. Rejected interface edits publish no value, relationship, provenance or result changes.
  6. Accurate display. Accepted values, available options and saved values agree after editing and reloading. An already-invalid stored selection is visibly invalid; opening its editor never presents another value as though that value had been saved.
  7. Reusable rules. Library callers and interface consumers can obtain dependency relationships and allowed choices, including choices under a proposed batch, from the same authoritative rules used for validation.
  8. No dependence on calculation history. The same edit has the same validation outcome before any Results have been computed and after loading a valid inputs-only or cached snapshot. A valid replacement relationship becomes the relationship used by later validation.
  9. Bounded work. Validation and option discovery target affected dependency paths and inputs. Adding unrelated modelings or unrelated objects does not cause those objects' inputs or calculations to be visited. Every job actually affected by a shared API change is checked.

3. Scope

In scope
  • Generic enforcement of the existing conditional-choice rules within and between objects.
  • Direct Python input changes, explicit batches and replacement of relationships along a dependency path.
  • Shared dependency and allowed-choice information for library validation, editor repair, field options and Simplified inputs selection requirements.
  • Automatic dependent repair and feedback in normal editing, aligned with Simplified inputs.
  • Accurate rendering of unsupported saved choices and preserved existing provenance behavior.
  • Regression coverage of video API choices and generic examples independent of that catalog.
Out of scope
  • New video models, resolution catalogs or environmental calculation formulas.
  • A new normal-editor control for redirecting jobs to another API; the library operation is covered.
  • Implicit automatic correction by the library or changes to authored inputs merely on reading them.
  • New dependency expression syntax, arbitrary constraint programming or collection wildcard paths.
  • A redesign of Simplified inputs, its eligible input kinds, inclusion policy or stored configuration.
  • A general rewrite of the calculation engine, persistence formats or composite editing workflows.

4. UX / interface

ExampleAccepted outcome
Two jobs use the same API: one at 720p, the other at 1080p. The new AI model allows 480p then 720p.The 720p job retains its resolution. The 1080p job changes to 480p. Both resolutions and the API's choice are saved together; a notice names the changed job.
A user explicitly submits 1080p with an AI model that only supports 480p and 720p. The edit is rejected with an explanation. The explicit resolution is not silently replaced.
A library caller redirects a 1080p job to that API without correcting the resolution. The operation fails and preserves the original API link and resolution.

5. Constraints

  • Respect the library constitution and the interface constitution: modeling validity belongs to the library; editor policy and persistence orchestration belong to the interface. No new framework dependency on concrete builders or interface code.
  • Keep one authoritative declaration of each conditional rule. Adding a dependency must not require a matching handwritten declaration on the controller.
  • Preserve existing missing-branch behavior: no declared branch is unrestricted; a declared empty branch allows no value. Preserve authored-input equality, including absence versus zero.
  • A valid standalone object must receive the same protection as an object linked into a System. Ordinary footprint calculations are not a prerequisite for input validation.
  • Existing valid JSON snapshots and Simplified inputs configuration continue to round-trip. Any necessary schema change follows the existing migration process; no schema change is assumed.
  • The Simplified inputs spec remains the reference for selection, provenance and save feedback. This feature extends equivalent conditional-value behavior to normal editing without expanding Simplified inputs eligibility.

6. Open questions

Already-invalid saved files. Earlier normal edits can have produced an invalid snapshot. Should loading reject it with a precise error, or allow correction while blocking affected Results until the inputs are repaired? Silent normalization is excluded. This decision is needed before the load/computation acceptance cases can be finalized.

Registration, cache lifecycle and exact library query contracts are design questions recorded in the draft plan for the planning stage.
