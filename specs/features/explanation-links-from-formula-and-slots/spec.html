Explanation links from formula and slots

Status: Spec — under review · 2026-10-19 · Library-driven, cross-repository

1. Problem and audience

After a model is saved and reloaded, the explanation of a calculated value is incomplete. In the introductory GenAI for Marketing video on social example, the Google Veo server's Instances manufacturing footprint formula reads * ( / ( * one hour ) ) + * ( / ( * one hour ) ): the operators and inline constants survive, the operand references do not. The value itself is correct.

The same reload leaves two neighbouring displays incomplete and they never recover, even after the missing values are computed later in the session. Measured on the saved and reloaded example:

  • Who: every interface user who opens a calculated attribute of a saved model, and every library user who calls explain() or draws a calculus graph on a loaded system. Explainability is a stated mission capability; a formula with holes undermines the trust the tool exists to build.
  • Frequency: every interface request rebuilds the model from its saved form, so every explanation of a stored footprint is affected, not only the first after an explicit reload. Only values that are saved with the model are affected; values recomputed on read already explain correctly. The affected values are the headline footprints, which are the ones users open most.
  • Why now: the cause is a second, separately stored copy of each value's dependency links that is resolved once at load time, when the referenced values do not exist yet. The library already holds a complete, values-free dependency graph for the whole model. Deriving the explanation links from what already exists removes the duplicate rather than repairing it.

Scope tradeoff. Rendering an explanation may compute the operands it shows. This is the same work the next click would trigger, and the same cost users already pay when opening an attribute that is not saved with the model. A design that renders stored topology without computing anything was considered and set aside as unmeasured optimization; see the decision record. The frequency assumption that explanations are opened far less often than models are saved is unverified.

2. Success criteria

Each criterion holds on a system computed, saved with its calculated values, and loaded again, with no computation between load and the check. "Complete" means identical to the same display on the system before it was saved.

  • The formula of a saved calculated value is complete: every operand appears with its label, operators and order are preserved, repeated operands appear each time, inline constants appear once per use.
  • The direct ancestors of a saved calculated value are complete and are exactly the attached operands of its formula.
  • The direct children of any value, input or calculated, are complete: every calculated value whose formula uses it is listed, whether or not that child was saved with the model.
  • The calculus graph of a saved calculated value reaches every input it depends on, through every intermediate value, with the same nodes and edges as before saving.
  • Holding for the Veo instances manufacturing footprint, the CDN server's use footprint and the system total footprint in the GenAI video example, and for the existing integration-test systems.
  • Saving a model after an input edit and reloading it yields the same completeness.
  • In the interface, the calculated-attribute side panel shows a complete formula, Input Variables list with magnitudes and Direct children list for a saved footprint after reload, and the calculus graph page shows every ancestor level. No interface view, presenter or template code changes to achieve this.
  • Loading a saved model performs no computation. Saving a model performs no computation beyond what the save boundary already requests. Explanation requests compute only the values they display.
  • Saved files no longer carry the per-value ancestor address list. Files that still carry it load without error.
  • All library and interface test suites pass; the library's big-system load and save performance gates hold.

3. Scope

Capability-level only. File paths, class/method/parameter names, refactor instructions, internal hypotheses, and "mirror pattern X" code-level decisions belong in plan.html, not here.
In scope
  • Resolving a saved formula's operand references on display, computing an operand when it is not yet available.
  • Defining a saved value's direct ancestors from its formula rather than from a separately stored list.
  • Defining a value's direct children from the model's dependency graph rather than from the saved values present at load.
  • Removing the per-value stored ancestor list and the load-time children reconstruction from the persistence contract, and tolerating the old key in existing files.
  • Library tests for completeness after a save-and-load round trip, including the formula, ancestors, children and graph of nested saved values.
  • Interface tests asserting the side panel and graph page are complete after reload. Owning architecture pages in both repositories updated to describe where links come from.
Out of scope (this iteration)
  • Rendering explanations from stored topology without computing operands (kept as the fallback if measured latency demands it).
  • Caching computed intermediates across interface requests.
  • Changing which values are saved with the model.
  • Making the calculus graph and the formula agree exactly. The graph may show a dependency that the formula does not, when a calculated value is read only to choose a branch. Accepted: the graph answers "what influences this", the formula "how is it computed".
  • Recording input reads during computation automatically (parked separately under specs/backlog/automatic-input-read-dependencies/).
  • Visual changes to the side panel or graph page.

5. Constraints

  • Constitution §1.1. The change stays inside the framework and serialization layers; no upward import is introduced.
  • Constitution §1.2 and §2.3. No compatibility branch beyond tolerating the removed key on load. Round-trip equality of saved values is preserved; the ancestor list is no longer part of the saved form, so the schema version bumps and a migration handler drops the key (§2.4).
  • Constitution §1.3. This is a removal of duplicated state, not a new abstraction. Each fact keeps one owner: expression in the formula, topology in the dependency graph, values in the slot cache.
  • Engine invariants. Loading computes nothing. Saving computes nothing. Bookkeeping that runs inside a computation or an invalidation never computes. Only display-time resolution may compute, and only the values it displays.
  • Performance. The library's big-system load and save gates in tests/performance_tests/ hold. A before-and-after latency measurement of the three example explanations is recorded in the plan as the baseline for the "optimize only if needed" decision.
  • Owning pages. Persistence contract and Recomputation: the reactive slot in the library; the interface's rendering page gains a line on where explanation links come from.
  • Changelog. One consolidated entry under Unreleased in each affected repository (§2.6).

6. Open questions

  • Should the direct children of a heavily used input, whose every consumer is computed when the list is rendered, be bounded in any way, or is the measured latency on the examples acceptable as is? Default: no bound; measure first.
  • Does any library consumer rely on children links of values that are not attached to a model object? None was found in the code; confirm during planning.
