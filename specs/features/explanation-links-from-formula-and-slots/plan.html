1.1 · Resolve a saved formula on display

Files efootprint/abstract_modeling_classes/explainable_object_base_class.py

A user opens a saved footprint in the side panel. The view get_calculated_attribute_explanation() calls the presenter, which reads explain_nested_tuples. For a value attached at load, that property deserializes the stored tree on first access and resolves each string leaf through get_attribute_from_flat_obj_dict(), which today peeks via peek_attribute_value(): a void operand becomes None, and _compute_formula_as_flat_tuple() drops the leaf but keeps its operators. That is the * ( / ( * one hour ) ) rendering.

Change. The resolver reads the attribute through ordinary attribute access, so a void computed slot is pulled by computed_attribute.__get__() and a dict address indexes the input dict or the computed-dict facade, whose item read pulls the sub-slot. The peeking body and its "never computes" docstring go.

efootprint/abstract_modeling_classes/explainable_object_base_class.py Proposed body of get_attribute_from_flat_obj_dict (replaces the peeking one)

def get_attribute_from_flat_obj_dict(attr_key: str, flat_obj_dict: dict):
    """Resolve a serialized (container id, attribute[, key id]) address to its live value, computing a
    void computed slot. Only the formula deserializer calls this, on display: an operand of an
    explanation is part of what is being explained."""
    container_id, attr_name, key_id = _parse_value_address(attr_key)
    value = getattr(flat_obj_dict[container_id], attr_name)
    if key_id:
        return value[flat_obj_dict[key_id]]
    return value

Why pulling here is safe, verified in this checkout:

  • After 1.2 removes the hydration path, the formula deserializer is the only caller of the resolver (today it has two: the formula at line 225 and load_ancestors_and_children_from_json() at lines 255 and 260).
  • Nothing reads explain_nested_tuples inside a computation. The compute closures only call record_calculus_edges_from_ancestry(), which reads direct_ancestors_with_id of the value the getter just returned; that value is fresh, so 1.2 serves it from the in-memory list without touching a stored formula.
  • Saving never deserializes: to_json() re-emits explain_nested_tuples_from_json when it is set, and the getter never clears it (only the setter does). The displayed-then-saved value therefore serializes byte-for-byte as before display.
  • The display runs outside any compute frame, so the pulls record no dependency edges; the pulled values attach to their slots exactly as a results-page read would attach them.

[PLAN-UPDATE-03] — PROPOSED

Current plan: the resolver reads getattr(container, attr_name), then indexes the result with the key for a dict address (snippet above).

Proposed change. For an address naming a computed dict, the resolver indexes the dict facade (computed_dict.facade(), found through computed_slots() of the container's class) instead of reading the attribute. The facade's __getitem__ pulls only that key's sub-slot and raises for a key outside the key collection. Plain attributes and input dicts keep ordinary attribute access.

Why. Reading a computed dict through computed_dict.__get__() pulls its key-set slot, whose closure pulls every element (line 285). Stored formulas do hold element addresses: freshly computed and saved, the complex integration system's formulas hold 17 element addresses out of 69 operand addresses, all elements of use_footprint_per_job, use_footprint_per_usage_pattern or instances_manufacturing_footprint_per_usage_pattern. Measured in this checkout on the complex integration system, saved and reloaded: resolving one use_footprint_per_job element costs 73 computations through the attribute and 20 through the facade. The extra computations are sibling elements the formula does not show, which the spec's constraint "explanation requests compute only the values they display" excludes.

Trade-offs. The resolver distinguishes computed dicts from input dicts, a branch the snippet did not have. It relies on facade item reads that the engine already uses to read one element inside a computation, so no new engine path is introduced.

Affected task: Task 2.

The computed operand is a fresh value attached to its slot, so its label, unit and magnitude are live. The presenter's symbol table and Input Variables list render it like any in-memory operand. Inline constants such as one hour are stored as dicts and keep deserializing through explainable_object_from_json() as unattached values.

1.2 · Direct ancestors derived from the formula

Files efootprint/abstract_modeling_classes/explainable_object_base_class.py

The calculus graph page's display_calculus_graph() hands the value to build_calculus_graph(), which walks direct_ancestors_with_id recursively and calls explain() on every node. For a loaded value the property runs load_ancestors_and_children_from_json() once, from the loader's inversion pass (1.4), while every non-serialized operand is void: addresses resolve to None, are filtered, and the _graph_links_hydrated_from_json flag prevents any later re-resolution. Measured: zero of six ancestors, before and after the operands are computed.

By construction a value's direct ancestors are the attached leaves of its formula: compute_explain_nested_tuples() collapses the parent tree at exactly the nodes that return_direct_ancestors_with_id_to_child() keeps (attached values), and both walk left parent before right parent, so a left-to-right leaf walk deduplicated by id reproduces the in-memory list and its order. Unattached leaves (inline constants, and intermediate nodes without ancestors) are excluded by both, as today.

efootprint/abstract_modeling_classes/explainable_object_base_class.py Proposed: a loaded value derives its list from the resolved formula on first read; fresh values are untouched

def _attached_formula_leaves(node):
    if isinstance(node, tuple):
        yield from _attached_formula_leaves(node[0])
        yield from _attached_formula_leaves(node[2])
    elif isinstance(node, ExplainableObject) and node.modeling_obj_container is not None:
        yield node


class ExplainableObject(ObjectLinkedToModelingObj):
    def initialize_calculus_graph_data_from_json(self, json_input, flat_obj_dict, sources_dict=None):
        self._sources_dict = sources_dict
        if "explain_nested_tuples" in json_input:
            self.explain_nested_tuples_from_json = json_input["explain_nested_tuples"]
            self._flat_obj_dict = flat_obj_dict
            self._direct_ancestors_with_id = None  # derived from the formula on first read

    @property
    def direct_ancestors_with_id(self):
        if self._direct_ancestors_with_id is None:
            self._direct_ancestors_with_id = list(
                {leaf.id: leaf for leaf in _attached_formula_leaves(self.explain_nested_tuples)}.values())
        return self._direct_ancestors_with_id

    @direct_ancestors_with_id.setter
    def direct_ancestors_with_id(self, value):
        self._direct_ancestors_with_id = value

The first read now happens on display (graph page, explain(), the test helper check_all_calculus_graph_dependencies_consistencies()) and pulls through 1.1. The graph walk from a saved root reaches fresh operands with live in-memory lists, then deeper saved values whose lists derive from their own formulas, then inputs. No change to calculus_graph.py.

Removed with this step: the __slots__ entries _keys_of_direct_ancestors_with_id_loaded_from_json, _keys_of_direct_children_with_id_loaded_from_json and _graph_links_hydrated_from_json (lines 121–123), their initialization in __init__ (lines 183–185), load_ancestors_and_children_from_json() itself, and the ancestor branch of initialize_calculus_graph_data_from_json(), whose trigger becomes the formula key instead of the ancestor key. "Logically dependent on" conditions are formula leaves, so they stay ancestors. The slot graph may hold a calculus edge the formula does not show (a computed value read only in a conditional, recorded by computed_attribute.__get__()); the graph page shows formula ancestry as today, which the spec accepts.

1.3 · Direct children derived from the slot graph

Files efootprint/abstract_modeling_classes/explainable_object_base_class.py · reactive_core/graph.py · reactive_core/computed_slots.py

The side panel's Direct children list calls the presenter's web_children(), which reads direct_children_with_id. Today the list is filled at load by invert_children_links_of_stored_values() from cached values only (and, in memory, by the bookkeeping in set_modeling_obj_container()), so void dependents never appear. A formula cannot supply children: void values have no formula. The slot graph can, since rebuild_dependency_graph() reinstalls every edge at load, values or not.

efootprint/abstract_modeling_classes/explainable_object_base_class.py Proposed property replacing the stored list (local import of slot_of_attached_value, as the module already does for other engine helpers)

@property
def direct_children_with_id(self):
    """Attached values whose formula uses this value: the calculus dependents of its slot, pulled."""
    if self.modeling_obj_container is None:
        return []
    slot = slot_of_attached_value(self)
    children = []
    for dependent in slot.dependents:
        # Only slots that attach an explainable value to their owner (computed attributes and
        # computed-dict elements) are children; bump nodes, key-set nodes and computed structures are not.
        if dependent.on_value_dropped is None or slot not in dependent.calculus_dependencies:
            continue
        children.append(dependent.pull())
    return children

slot_of_attached_value() gives the node for a computed value through its backpointer and for an input through its bump node, so one property serves both; the same resolution already serves record_calculus_edges_from_ancestry(). dependents is the union of calculus and structural readers. Two filters, both applied before pulling:

  • slot in dependent.calculus_dependencies (line 132) keeps formula consumers and drops structural-only readers, as the decision record asks.
  • dependent.on_value_dropped is not None (line 98) keeps the slots that hold an attached explainable. Only computed_attribute.slot() and computed_dict.sub_slot() pass _release_value; the computed-dict key-set node (_on_value_dropped = None) and computed_structure.slot() do not. Without this check a child listing could pull a computed structure (the key-set closure at line 280 pulls every element of its dict) and then discard the non-explainable result. See decision 1 for the marker choice.

Pulling a dependent computes its void subtree. Measured on the saved and reloaded GenAI video example (baseline table): the heaviest list, the children of the country's carbon intensity, pulls seven dependents through 82 computations in about 5 ms. The spec's "bound the list?" question is answered: no bound. A dependent whose getter raises propagates the error to the request, exactly as opening a non-serialized attribute does today; no recovery is added.

[PLAN-UPDATE-02] — PROPOSED

Current plan: children are the calculus dependents of the value's slot that carry a drop callback, each pulled (this step); the engine is unchanged (graph.py "No edit").

Proposed change. (a) A slot that leaves the model severs its own dependency edges: each stale sub-slot that computed_dict.discard_stale_keys() pops from the registry, and every slot of an object removed by ModelingObject.self_delete() (beside its _drop_value() loop), calls replace_dependencies() with no arguments. Edges of live slots are untouched. (b) The children property keeps a pulled dependent only if slot in dependent.calculus_dependencies still holds after the pull.

Why. dependents is a deliberate over-approximation for invalidation: a void slot keeps the edges of its last successful computation (ReactiveSlot docstring). Two paths leave dead slots wired in: discard_stale_keys() pops a stale sub-slot (line 274) without removing its edges, and self_delete() drops values but keeps edges. Replayed in this checkout, run_test_add_usage_pattern up to its post-reset loop: after rollback and deletion of the added usage pattern, the country's carbon intensity keeps six explainable calculus dependents, one of them the new device's use_footprint_per_usage_pattern sub-slot keyed by the deleted pattern; pulling it raises KeyError. The country's timezone also keeps the deleted pattern's utc_hourly_occurrences as a dependent. The property as planned would therefore fail the existing post-reset loops (simple, edge, edge, journey). With (a) monkeypatched into the same replay, three dependents remain, all live and pulling cleanly, and no surviving slot lists a deleted object's slot. For (b), a void dependent whose last computation read this value only under a branch that no longer holds would otherwise be listed after recomputing without it; the check is one set lookup.

Trade-offs. (a) touches the reactive core, a FULL review surface, but removes edges only from slots no longer reachable from the model, so no live slot can miss an invalidation. Objects detached without deletion (a network left behind by a rollback) keep their edges: while they still read the value they are listed, as live in-memory consumers. A reloaded interface model never holds such slots, since the loader rebuilds only the saved graph. Alternative: filter at read time on owner liveness; slots carry no owner reference, so this adds state to every slot. Rejected.

Affected tasks: Task 1 (new, carries (a)) and Task 2 (carries (b) and depends on (a)).

Removed with this step: the _direct_children_with_id slot and setter, add_child_to_direct_children_with_id(), remove_child_from_direct_children_with_id(), all_descendants_with_id (no callers outside its unit test), and the ancestor/children loops in set_modeling_obj_container() lines 339–344 and 349–350, which keeps its label check, the base call and finalize_explanation(). That removal is also a correctness requirement: with 1.2, the detach loop would deserialize a formula and pull inside _release_value(), i.e. during an invalidation wave. Its docstring loses the "ancestor children links" clause. all_ancestors_with_id stays (used by ExplainableObjectDict.all_ancestors_with_id).

Spec open question 2 (children of values not attached to a model object): no production consumer exists. Only two unit tests build such links by hand, the children bookkeeping tests and one assertion that attaches a child outside the engine; both are rewritten (values attached by hand have no slot edges and therefore no children, which is the intended contract).

3. Decisions for review

1 · Which slots count as children — ACCEPTED 2026-10-19: reuse the drop callback

The children filter in 1.3 must skip computed structures and key-set nodes before pulling. The proposal reads on_value_dropped, which only the two explainable-holding slot kinds set, with a comment at the filter. The alternative is an explicit boolean on ReactiveSlot.__init__() set by the same two descriptors. Decision: reuse the callback; it already encodes "this slot attaches an explainable to its owner", and a second flag would have to be kept in step with it.
