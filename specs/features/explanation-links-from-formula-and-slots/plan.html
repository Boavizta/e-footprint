1.1 · Resolve a saved formula on display

Files abstract_modeling_classes/explainable_object_base_class.py

A user opens a saved footprint. The interface presenter reads explain_nested_tuples, which deserializes the stored tree on first access and resolves each leaf address through get_attribute_from_flat_obj_dict(). Today that helper peeks, so a void operand becomes None and the flattener drops the leaf but keeps its operators. The change: the resolver reads the attribute normally, which pulls a void computed slot.

abstract_modeling_classes/explainable_object_base_class.py Proposed resolver (replaces the peeking body)

def get_attribute_from_flat_obj_dict(attr_key: str, flat_obj_dict: dict):
    """Resolve a serialized (container id, attribute[, key id]) address to its live value, computing
    a void computed attribute. Display-time only: the formula is the sole caller."""
    container_id, attr_name, key_id = _parse_value_address(attr_key)
    value = getattr(flat_obj_dict[container_id], attr_name)
    if key_id:
        return value[flat_obj_dict[key_id]]
    return value

Safety of pulling here rests on three facts verified in this checkout: the formula property has a single non-test reader, the interface presenter; no getter calls explain() during a computation; to_json() re-serializes the raw stored tuple when present, so saving never deserializes. After 1.2 removes the ancestor hydration, the formula deserializer is the resolver's only caller, so there is one resolver with one policy. The dict-container lookup keeps using peek_attribute_value(), which stays as the bookkeeping-side primitive.

The computed operand is a fresh value attached to its slot, so its own formula, label and unit are live. The presenter's symbol table and Input Variables list render it like any in-memory operand, magnitudes included.

1.2 · Direct ancestors derived from the formula

Files abstract_modeling_classes/explainable_object_base_class.py · utils/calculus_graph.py

The calculus graph page calls build_calculus_graph(), which walks direct_ancestors_with_id. For a loaded value that property runs load_ancestors_and_children_from_json() once, at load time, from the loader's inversion pass; void addresses are dropped and a flag prevents any later re-resolution. The measured result is zero of six ancestors, before and after the operands are computed.

By construction a value's direct ancestors are the attached leaves of its formula: compute_explain_nested_tuples() collapses the parent tree at exactly the nodes return_direct_ancestors_with_id_to_child() keeps. So the loaded case derives the list from the resolved formula instead of a stored key.

abstract_modeling_classes/explainable_object_base_class.py Proposed property; the in-memory path for fresh values is unchanged

@property
def direct_ancestors_with_id(self):
    if self._direct_ancestors_with_id is None:  # loaded value: derive from the formula once
        seen, ancestors = set(), []
        for leaf in _attached_leaves(self.explain_nested_tuples):
            if leaf.id not in seen:
                seen.add(leaf.id)
                ancestors.append(leaf)
        self._direct_ancestors_with_id = ancestors
    return self._direct_ancestors_with_id

Fresh values keep building the list in __init__ from their parents, which record_calculus_edges_from_ancestry() reads inside the compute closure; that path never touches a stored formula. "Logically dependent on" leaves are formula leaves, so conditions wrapped today stay ancestors. Unattached constants such as one hour are excluded, matching the current rule. Removed with this step: _keys_of_direct_ancestors_with_id_loaded_from_json, _graph_links_hydrated_from_json, load_ancestors_and_children_from_json(), and the ancestor branch of initialize_calculus_graph_data_from_json(), which keeps installing the formula, the flat object dict and the sources dict.

Because the first access now happens on display and pulls, the graph walk from the root reaches fresh operands with live ancestor lists, then cached serialized values whose own lists derive from their formulas, then inputs. No change to calculus_graph.py.

1.3 · Direct children derived from the slot graph

Files abstract_modeling_classes/explainable_object_base_class.py · abstract_modeling_classes/reactive_core/graph.py

The side panel's Direct children list calls the interface's web_children(), which reads direct_children_with_id. Today that list is filled by invert_children_links_of_stored_values() from cached values only, so void dependents never appear (zero of five for a job input). Formulas cannot supply children, since void values have none. The slot graph can: it is reinstalled complete at load by rebuild_dependency_graph().

abstract_modeling_classes/explainable_object_base_class.py Proposed property replacing the stored list

@property
def direct_children_with_id(self):
    if self.modeling_obj_container is None:
        return []
    slot = slot_of_attached_value(self)
    children = []
    for dependent in slot.dependents:
        if dependent.getter is None or slot not in dependent.calculus_dependencies:
            continue  # bump nodes and structural-only readers are not formula children
        value = dependent.pull()
        if isinstance(value, ExplainableObject):
            children.append(value)
    return children

slot_of_attached_value() gives the node for a computed value through its backpointer and for an input through its bump node, so the same property serves both. dependents is the union of calculus and structural readers; filtering on calculus_dependencies keeps formula consumers and drops computed-dict key-set slots. A computed-dict facade pulled this way is not an ExplainableObject and is skipped; its sub-slots are dependents in their own right and appear as entries. Pulling a dependent computes its void subtree; this is the heaviest display in the feature and the one to measure first.

Removed with this step: _direct_children_with_id and its setter, add_child_to_direct_children_with_id(), remove_child_from_direct_children_with_id(), all_descendants_with_id (no callers), and the children bookkeeping inside set_modeling_obj_container(), which keeps its label check, the base call and finalize_explanation(). The value-drop path through _release_value() then only unsets the container. Invalidation never used these lists; it is slot-based.

3. Decisions for review

1 · Migration handler versus silent tolerance of the removed key

Constitution §2.4 asks for a handler and a version bump when the schema changes. The leaner alternative is a loader that ignores unknown keys, which it may already do. Recommendation: the handler, so the contract stays explicit and the fixtures are regenerated once; confirm in spec-plan whether the loader currently rejects or ignores the key.

2 · Unbounded pulling of children

Listing the children of a widely used input computes every consumer's void subtree. Recommendation: no bound, measure on the examples first, and record the numbers here. The stored-topology rendering from the decision record is the fallback if the baseline is unacceptable.

3 · Graph and formula may differ by a node

Ancestors derive from formula leaves, so the calculus graph page shows formula ancestry, as today. The slot graph additionally records computed values read only in conditionals. Nothing in this feature displays those extra edges; accepted and out of scope.

4 · Land A and B together or sequentially

With A alone, the loader's inversion pass would trigger the new derived ancestor property at load time and pull. Either B lands with A, or A keeps the inversion pass reading the raw stored keys with a peek until B removes it. Recommendation: one task for A and B, since both edit the same two properties.
