Edge wireless networks — library modeling

Status: Spec — under review · 2026-11-02

1. Problem and audience

An edge device's wireless link is invisible in e-footprint today. The only network object charges electricity per gigabyte transferred, which the literature review of 2026-07-06 shows is the wrong physics for IoT links: a battery sensor spends most of its energy sleeping, waking for keep-alive polls and sending a few short frames, and the gateway or base station it talks to draws constant power whatever the traffic. Nothing in the library lets a user say "this sensor talks LoRaWAN once every five minutes through a gateway on site" and get a defensible energy and carbon figure for that link.

AudienceOutcome
Industrial users modeling deployed fleets (a mission audience) Compare radio technologies, message cadence, payload size and poll period for a fleet, and see the on-site gateway and the operator network as their own footprint lines.
Hardware-aware engineers Document their own radio module and gateway measurements (sleep current, transmit power, fabrication footprint) with provenance, and optimize against them.
Researchers and consultants Start from literature-sourced defaults for six technologies, each value carrying its source, and reproduce published figures.

Why now. Edge modeling (devices, components, groups, deployment patterns) shipped in both repositories, so the radio link is the main missing piece for IoT fleets. The modeling approach is settled by the 2026-07-06 literature note and spec draft: a power model with three additive terms (sleep floor, per-message energy, synchronization energy), a user-owned gateway as a countable unit, and a per-device-hour allocation of operator networks.

Scope tradeoffs taken.

  • Power model, never kWh/GB for the device radio and the gateway. The existing per-gigabyte network stays the backhaul model from the gateway to the cloud.
  • Six technologies, one parameter table. LoRaWAN, SIGFOX, NB-IoT, BLE, WiFi in power-saving mode, and Thread. Adding a technology later is a table row, not a code path. The only per-technology specifics are SIGFOX's built-in triple transmission and the operator-side allocation rows of NB-IoT and SIGFOX.
  • No distance scaling of transmit power and no segment chaining. Technology choice and datasheet transmit power already encode range class. Mesh technologies get a single integer hop multiplier, default 1.
  • Owned gateway as its own countable hardware unit. Sized by the same group composition as devices, with no devices-per-gateway input and no sharing-fraction input. A gateway shared with other tenants is expressed through a fractional group count or scaled power and fabrication inputs.
  • Operator networks are an allocation, not an object. NB-IoT and SIGFOX charge a per-device-hour energy and embodied share from per-subscription figures. Allocation key is time per subscriber, never per gigabyte.
  • Backhaul volume is not charged twice. Message payloads reach the cloud through the server-side jobs the user already models on the existing per-gigabyte network. This spec adds no second data path (see open question 1).
  • Battery-to-lifespan coupling deferred. Device and component lifespans keep their existing defaults and overrides.

Unverified frequency assumptions. Most IoT models use one radio technology per device and uplink-dominated periodic messaging. Downlink-heavy traffic and multi-radio devices are not measured needs and are out of scope.

2. Success criteria

Each criterion is observable through the library's public API and its tests.

  1. Technology defaults with provenance. A user creates a network interface for an edge device by naming one of the six technologies. Every physical parameter (transmit, receive and sleep power, bitrate, frame overhead, maximum payload per frame, fixed energy per message, receive listen time per message, synchronization period and energy, hop count, packet error rate, operator shares, fabrication footprint, lifespan) is filled from the technology table, carries a literature source, and can be overridden individually with the user's own source.
  2. Messaging drives the link. A user attaches a messaging need to the interface with a weekly messages-per-hour pattern and a payload size. The interface's hourly energy is the sum of a sleep floor, a per-message term and a synchronization term, and flows into the device's hourly energy, use footprint and manufacturing footprint like any other component.
  3. Published figures reproduce. With default parameters, the model reproduces the following within 30 % (the accuracy class of validated analytical models in the literature): LoRaWAN energy per message against Casals et al. 2017 for a 1 message per 5 minutes scenario, SIGFOX energy per 12-byte message against Gomez et al. 2019, and a Thread leaf's average current at a 10-second message period against Kim et al. 2019.
  4. The three terms behave as the literature says. At one message per day the sleep floor is more than 90 % of interface energy for asynchronous technologies. For Thread at the default 2.5-second poll period the synchronization term dominates. A payload larger than the technology's maximum frame payload costs proportionally more frames. A packet error rate of 0.2 multiplies airtime by 1.25. SIGFOX counts three transmissions per message.
  5. Owned gateway. A user creates a gateway (constant power, fabrication footprint, lifespan), links interfaces to it, and sees it as its own source in the system footprint and in the Sankey, never folded into the devices. Its hourly energy and manufacturing scale by its group count and the deployment pattern's parallel deployments. A gateway in no group counts as one per deployment. Linking a gateway from an operator-side technology is refused with a clear error, and a gateway whose lifespan is shorter than a pattern's usage span raises the same error class as a device does.
  6. Operator-side technologies. An NB-IoT or SIGFOX interface adds its per-device-hour operator energy (converted with the pattern's country carbon intensity) and embodied share to the device's use and manufacturing footprints. The four gateway technologies carry zero operator share.
  7. Fleet composition. A group accepts a gateway in its device counts beside devices; nested groups unroll the gateway count exactly as they unroll a device count.
  8. Existing behavior unchanged. Existing edge device, component, group and integration tests pass without modification. Existing saved systems load unchanged.
  9. Serialization and documentation. New objects round-trip through JSON with their calculated attributes; they are registered for the Sankey and the canonical-class registry; the reference documentation builds strictly from their docstrings and parameter descriptions; the changelog carries one consolidated entry.

3. Scope

Capability-level only. Class, attribute and module names, default values and refactor steps live in plan.html; the modeling formulas are in §5.
In scope
  • A radio interface component for edge devices, parameterized by technology with sourced, overridable defaults for LoRaWAN, SIGFOX, NB-IoT, BLE, WiFi (power-saving mode) and Thread.
  • A messaging need (weekly messages-per-hour pattern, payload size) that loads the interface, with fragmentation, retransmission and hop multipliers.
  • Three-term hourly energy for the interface: sleep floor, per-message, synchronization.
  • A user-owned gateway object: constant power, fabrication footprint, lifespan; linked from interfaces; counted through groups; its own footprint source.
  • Per-device-hour operator energy and embodied shares for NB-IoT and SIGFOX.
  • Radio module fabrication footprint amortized like any component.
  • Registration, serialization, documentation metadata and changelog for the new objects.
  • Validation tests against the published figures listed in the success criteria.
Out of scope (this iteration)
  • Mesh routing detail beyond the hop multiplier; mains-powered Thread routers along the path.
  • Downlink-heavy traffic and multi-radio devices.
  • Wired LAN and WAN links (constant-power switches, PoE): a separate topic closer to the existing network and server modeling.
  • Battery capacity driving device lifespan (v2: lifespan = battery energy / average power, which creates a calculation loop to design carefully).
  • A sharing-fraction input for an owned gateway (fractional group count or scaled inputs cover it, stated in the user documentation).
  • A second backhaul data path from message payloads to the per-gigabyte network (see open question 1).
  • Always-on WiFi devices on mains power: modeled as plain device power draw today.
  • Further technologies (TSCH, 802.11ah): a table row each when needed.

4. Library API and object graph

What a library user writes once the feature ships. Names are the draft's working names; the plan settles them.

interface = EdgeNetworkInterface.from_technology(
    "LoRaWAN",                                   # six defaults loaded, each overridable
    p_sleep=SourceValue(2.1 * u.uW, Source("bench measurement 2026-05")),
)
device = EdgeDevice("soil sensor", components=[cpu, ram, interface], lifespan=...)
messaging = RecurrentMessagingNeed(
    "hourly readings", edge_component=interface,
    messages_per_hour=weekly_pattern([...]),     # 168 values
    payload_size=SourceValue(24 * u.B),
)
gateway = EdgeGateway("farm LoRa gateway")       # 5 W, 25 kg CO2e, 6 years by default
interface.edge_gateway = gateway                 # refused for NB-IoT and SIGFOX
farm = EdgeDeviceGroup("farm", edge_device_counts={device: 80, gateway: 1})
pattern = EdgeUsagePattern(..., network=backhaul, country=france)

Devices per gateway (80) is read from the group, never entered twice. The optimization loop this enables: swap technology, batch messages (payload up, count down), compare chips by sleep power, tune the poll period, resize the fleet per gateway through group counts.

Hourly carbon for one deployed device-hour, in words: interface energy (sleep floor + messages × energy per message + syncs × energy per sync) times the country's carbon intensity, plus the radio module's amortized fabrication, plus either the operator share (NB-IoT, SIGFOX) or the gateway's share through its own footprint line (LoRaWAN, BLE, WiFi, Thread), plus backhaul through the server-side jobs on the existing network. The formulas are laid out step by step in §5; default values and their sources are in the plan.

5. Modeling logic

The whole model in six steps, read top to bottom. Every hourly quantity is evaluated per hour (Δt = 1 h) over the modeling period; every symbol is an input the user can override (default from the technology table) unless marked computed.

Step 1 — frames and airtime of one message

Nframes = ⌈ payload ÷ max payload per frame ⌉

bframe = payload × 8 ÷ Nframes + overhead per frame

Ntx = transmissions per message ÷ (1 − packet error rate)

tair = Ntx × Nframes × bframe ÷ bitrate

A message larger than the technology's frame payload is split into frames, each paying the protocol overhead again. Lost frames are re-sent (1 ÷ (1 − PER) expected transmissions). SIGFOX always sends each frame three times, so its "transmissions per message" is 3; it is 1 elsewhere.

Step 2 — energy of one message

Emsg = hops × ( fixed energy per message + tair × Ptx + listen time per message × Prx )

Fixed energy covers wake-up and idle between radio states; listen time covers acknowledgement or receive windows. The hop multiplier (default 1) charges mesh relaying to the originating device.

Step 3 — hourly energy of the radio interface, per device

Nmsg(t) = messages per hour from the messaging needs (weekly pattern replayed over the deployment calendar) — computed

Nsync(t) = max( 0, Δt ÷ sync period − Nmsg(t) ) — computed; 0 for asynchronous technologies (sync period = ∞)

Einterface(t) = Psleep × Δt + Nmsg(t) × Emsg + Nsync(t) × energy per sync + operator energy per device-hour

Three terms plus the operator share. The sleep floor is paid every hour whether or not anything is sent. Synchronization counts keep-alive polls or beacon listens; a data frame doubles as a sync, hence the subtraction. The operator term is zero for the four technologies with an owned gateway.

Step 4 — from one device to the fleet (existing edge mechanics)

fleet energy(t) = Einterface(t) × deployments in parallel(t) × total units of the device

use footprint(t) = fleet energy(t) × grid carbon intensity of the country

manufacturing footprint(t) = ( interface fabrication ÷ interface lifespan × Δt + operator embodied per device-hour ) × deployments in parallel(t) × total units of the device

"Deployments in parallel" comes from the edge usage pattern; "total units" from the device's group counts. The interface is one more component of the device, so these lines add to the CPU, RAM and chassis lines the device already carries.

Step 5 — owned gateway (LoRaWAN, BLE, WiFi, Thread)

gateway energy(t) = gateway power × Δt × deployments in parallel(t) × total units of the gateway

gateway use footprint(t) = gateway energy(t) × grid carbon intensity

gateway manufacturing footprint(t) = gateway fabrication ÷ gateway lifespan × Δt × deployments in parallel(t) × total units of the gateway

Constant power, independent of traffic. "Total units of the gateway" comes from its own group counts, one per deployment when it is in no group. The gateway is its own footprint line; for the Sankey its footprint is split across the messaging needs that reach it in proportion to the number of radios each represents (device units × occurrences), the same time-per-subscriber key as the operator share.

Step 6 — backhaul

backhaul footprint = data transferred by the server-side jobs × network energy per gigabyte × grid carbon intensity — existing

Unchanged. Message payloads reach the cloud through the jobs the user already models; the messaging need adds no second data path (open question 1).

6. Constraints

  • Constitution gates. Three-layer separation; new modeling classes registered in the class registry and the Sankey structure; JSON round trip for every new object; a migration handler and schema version bump only if the JSON schema of existing objects changes (new classes alone are additive); strict docs build from docstrings and parameter descriptions; changelog entry.
  • No backward compatibility burden beyond loading existing saved systems: the group composition type may widen to a shared parent without shims.
  • Leanness. One technology table with sources; no per-technology code path except SIGFOX's triple transmission and the operator rows. Existing per-component mechanisms (hourly need replay, affine power curve, amortized fabrication, attribution atoms) are reused, not duplicated.
  • Provenance. Every default is a sourced value naming its paper or vendor measurement. Vendor-measured Thread figures are flagged as such; the Thread defaults are best-in-class hardware and the user documentation says so.
  • Units end to end through pint: a dimensional check is part of the tests.
  • Runtime cost. Interface energy is one more hourly series per (need, pattern), the same size as any component need; no new timeseries resolution.
  • Descriptions. Class docstrings and parameter descriptions are the single source of truth for what each object and input means, written for readers with no modeling background.
  • Owning architecture pages: specs/architecture/layers-and-modeling.html, relationships.html, attribution.html, persistence.html.

7. Open questions

  1. Backhaul mechanism (recommendation: no new data path). The draft says the existing per-gigabyte network is "fed by message payloads volume". Today that network only sees data through jobs, and an IoT model that reaches the cloud already has a server-side job carrying the ingested bytes. Adding a payload-to-network path would double count whenever such a job exists and would add a second data mechanism to the network object. Recommendation: the messaging need carries no backhaul volume; the user documentation says backhaul is modeled by the server-side job's data transferred. Confirm or ask for the second path.
  2. LoRaWAN spreading factor (recommendation: not a dedicated input in v1). The draft's API sketch passes a spreading factor. A dedicated selector is a per-technology code path. Bitrate and maximum payload are already overridable per interface, and the documentation can tabulate the SF7 to SF12 values. Confirm, or ask for the selector.
  3. Default figures to pin during implementation. Operator per-subscription energy and embodied split for NB-IoT and SIGFOX (Malmodin 2018, Ruiz 2022); radio module and gateway fabrication footprints from Pirson & Bol functional blocks; each technology column verified against its paper's tables. Placeholder values are acceptable while flagged as e-footprint hypotheses.
  4. Gateway breakdown by linked device. The Sankey needs the gateway's footprint split across the usage paths that reach it. Is a user-facing breakdown of the gateway by device wanted beyond that, or is the system-level gateway line enough for v1? Recommendation: the Sankey split only.
