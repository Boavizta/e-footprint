Multiple usage journeys per pattern — Implementation plan

Status: Plan — under review · 2026-09-01 · Spec: spec.html

1. Approach

This is a library-driven cross-repository change. In the library, replace the web pattern's singular journey with a weighted structural relationship and the edge pattern's singular journey with a list relationship. Move edge deployment lifetime and active-deployment concurrency onto the edge pattern. Keep journeys reusable across patterns; relationship context supplies web weight or edge deployment context. Add relationship guards so construction and transactional mutations reject empty collections and web weights that are not strictly positive.

Refactor downstream computations to iterate explicit pattern → journey → child paths. Web step and job coordinates carry journey identity because journey weight and temporal position can change the hourly series. Edge calculations instead centralize their actual containment paths in one small typed inventory on the pattern: physical need series aggregate once per pattern and need, while attribution cells retain bundle identity and split that aggregate by scalar path multiplicities. Edge hardware totals use one pattern-level deployed-device series; bundle needs add before component power and footprint calculations, preventing physical fabrication and idle/base energy from being repeated per bundle.

Proposed domain-facing names
  • UsagePattern.usage_journeys: weighted mapping with weight label “Journeys per pattern occurrence”.
  • UsagePattern.hourly_occurrences and utc_hourly_occurrences: pattern occurrences before journey-specific weights are applied.
  • EdgeUsagePattern.edge_usage_journeys: unweighted unique list.
  • EdgeUsagePattern.usage_span, hourly_deployment_starts, utc_hourly_deployment_starts, and nb_deployments_in_parallel: deployment-owned lifetime and active count.
  • EdgeUsageJourney loses usage_span and its pattern-keyed active-journey count; it becomes a reusable functionality bundle.

3. Calculation and relationship details

Web weighting and coordinates
  • Convert constructor input through the existing weighted-relationship helper, but add a pattern-specific guard that rejects an empty mapping and weights less than or equal to zero.
  • Compute each journey's parallel count from the shared occurrence series multiplied by that journey's relationship weight.
  • Reset step-delay accumulation for each journey. Replace the step's current pattern-only occupancy cache with a lazy computed dictionary keyed by a stable (usage pattern, usage journey) coordinate; the owning step supplies the third identity.
  • Extend a web JobOccurrenceCoordinate to (usage pattern, usage journey, step). Both average occurrences and transferred data keep using the existing per-coordinate computed-dictionary cache and stable-key pruning.
  • Regular device totals sum each selected journey's weighted parallel count and do not materialize step coordinates. Device attribution requests the step-coordinate cache and emits one atom per actual journey/step path.
  • When one job appears in several paths, keep its pattern-level physical total aggregated while retaining the separate web coordinates required for attribution.
  • Keep journey collection order semantically irrelevant; do not expose reorder controls.
Edge deployment aggregation
  • Compute active deployments once from deployment starts and pattern usage span. Every bundle uses that same series and pattern context.
  • Build one small typed EdgeContainmentInventory as a non-serialized computed structure on the pattern. It contains server-need paths (journey, edge function, server need, nb_occurrences) and component-need paths (journey, edge function, device need, component need, nb_occurrences). Keep the implementation domain-specific and direct rather than introducing a generic relationship-inventory framework.
  • Derive each path's integer nb_occurrences from multiplicities in the existing nested lists. Each recurrent-need calculation retains the concrete local name nb_of_occurrences_of_self_within_usage_pattern and obtains it by summing that field across its inventory paths. Attribution reuses the same values as path.nb_occurrences / nb_of_occurrences_of_self_within_usage_pattern.
  • For each recurrent component need or server need, generate and cache one aggregate hourly series per (pattern, need). The deployment series supplies its calendar range only; multiply the expanded unitary profile by nb_of_occurrences_of_self_within_usage_pattern, then multiply by active deployments in the downstream physical total. Distinct needs on one component add; an identical need reached twice contributes twice through its number of occurrences, without allocating a second hourly series for the second bundle.
  • Apply chassis, component fabrication, unused-component fabrication, and idle/base energy to the active deployment count once. Apply dynamic component demand after bundle aggregation.
  • Keep the edge Job base cache at (edge usage pattern, recurrent server need). Create separate journey-aware attribution cells from the inventory and apply their scalar normalized path shares to that shared series. Edge-device atoms use the same rule for component-need paths.
  • Store explicit journey identity on edge attribution cells and atoms, but do not add journey to edge hourly cache keys: attribution identity is finer than the reusable computation identity.
Cache lifetime and memory
  • Keep web step and Job coordinate mappings lazy and persistent like the existing Job coordinate mechanism. They are shared by multiple consumers and lifecycle phases; source-scoped eviction would otherwise repeat time-series and convolution work.
  • Do not add per-bundle edge hourly caches, cached atom collections, or caches in the attribution core. The edge containment inventory retains only object identities and integer counts.
  • Preserve the recent attribution-memory boundary: large source-owned attribution helper structures remain transient=True, each source reduces hourly atoms to scalar rows, and those transient helpers are evicted after the source is consumed.
  • Do not add transient semantics to computed_dict in this feature unless profiling first demonstrates a material retained-memory regression and a separately reviewed lifetime design covers all shared consumers and dependent structures.
Cardinality enforcement

Use domain guards that read relationship membership/weights so a live mutation participates in ModelingUpdate and rolls back atomically. Also reject empty constructor input and validate raw loaded pattern records before hydration makes them live, because the current loader intentionally does not compute guards. The interface mirrors the invariant by preselecting the first journey and disabling removal of the final relationship; it is not the source of truth.

4. Persistence migration

  1. Bump the library/schema major version.
  2. For every web pattern, convert the singular journey id into a weighted relationship containing that journey at weight 1 with the standard relationship-weight label.
  3. Rename the web occurrence inputs to hourly_occurrences and utc_hourly_occurrences.
  4. For every edge pattern, convert the singular journey id into a one-item list. Copy that journey's usage span, including source metadata, onto the pattern and rename its deployment-start input.
  5. After all edge patterns have received a span, remove span from edge journeys. A journey shared by several legacy patterns gives each pattern the same copied span; standalone journeys simply become span-free reusable bundles.
  6. Remove computed entries whose names or coordinate shapes no longer exist and ignore the old calculation graph. Preserve compatible serialized system totals as the existing version baseline where practical; authoritative inputs are always the migration gate.
  7. Verify inputs-only and calculated-state files, exact new-version round trips, shared-journey migration, and footprint equivalence for representative web and edge models.

No Django database migration is required: interface model state remains session-held library JSON.

5. Cross-cutting concerns

  • Library tests: cover weights below/above 1, two journeys with distinct and shared steps/jobs, two edge bundles with distinct and shared needs, one journey reused by several patterns, physical edge-footprint non-duplication, last-link mutation rollback, dependency invalidation after membership/weight changes, and all old single-journey behavior at weight 1.
  • Attribution tests: extend conservation harness cases with multiple journeys under one pattern and reused lower-level objects. Assert journey nodes and matrix rows remain distinguishable and sum to eager footprint streams. Assert each need's nb_of_occurrences_of_self_within_usage_pattern equals the sum of its inventory paths' nb_occurrences and normalized path shares sum to one.
  • Serialization tests: round-trip both relationship types and weight sources; add the version migration and verify old calculated state cannot attach under obsolete coordinates.
  • Interface tests: unit snapshots for the weighted/multi-select forms and moved usage span; integration create/edit/delete flows including the last-link invariant; results-view smoke coverage; one non-redundant E2E flow for weighted web journeys and one for multiple edge bundles.
  • Recomputation: verify recreated web coordinates select stable computed-dictionary sub-slots, a journey weight or membership edit invalidates only the affected coordinate cone, departed paths are pruned, and edge relationship edits rebuild the containment inventory and its dependent aggregate series.
  • Performance and memory: update benchmark accessors and big-system generation. Exercise cold-sankey, results-primed-sankey, and direct-attribution scenarios with many journeys and shared children; compare materialized coordinate-subslot counts, peak and retained memory, and reactive callback counts. Assert hourly cache growth follows actual web paths and distinct edge (pattern, need) pairs, never a Cartesian product or edge bundle-path count.
  • Docs: update library relationship, persistence, attribution, and modeling pages; update interface architecture's relationship/form section and user-journey design/help text. This is the non-trivial relationship pattern documentation required by both repositories' agent guidance.
  • Release notes: one consolidated entry in each repository under ## [Unreleased] when implementation completes.

6. Risks

  • Edge physical footprint multiplied by bundle count. Mitigation: make active deployments pattern-owned and test fixed fabrication/idle totals against a one-bundle baseline while adding bundle demand.
  • Coordinate collisions for reused children. Mitigation: journey is required in web computation coordinates and in all attribution cells/atoms; edge aggregate cache coordinates deliberately omit journey and split through the canonical inventory's scalar path shares.
  • Missed dependency invalidation after relationship edits. Mitigation: use the established weighted/list relationship containers, exercise membership and weight mutations, and compare incremental results with clean reconstruction.
  • Attribution drift or double allocation. Mitigation: ground up atoms by explicit containment path, derive aggregation and normalized shares from the same inventory, and gate every affected source through the conservation harness.
  • Retained hourly arrays grow with journey reuse. Mitigation: keep caches lazy, avoid per-bundle edge arrays, measure the established cold/primed/direct memory scenarios, and preserve source-scoped eviction of transient attribution helpers.
  • Legacy calculated state attaches under obsolete names. Mitigation: the version handler removes incompatible computed entries/graph topology and forces fresh computation.
  • UI accidentally nests or clones reusable journeys. Mitigation: keep journeys as top-level cards, edit relationships in the pattern form, and generate multiple leader lines from the pattern wrapper.
  • Terminology remains singular. Mitigation: audit docstrings, form labels, examples, comparisons, generated docs, selectors, and performance helpers for old field names.

7. Alternatives considered

  • Unweighted lists on both sides. Rejected because a web population cannot express journeys occurring at different average frequencies without duplicating its pattern.
  • Weights on both sides. Rejected because an edge weight ambiguously mixes bundle multiplicity, fleet adoption share, and duty cycle; recurrent needs already own intensity.
  • Keep usage span on edge journeys and require equal spans. Rejected because deployment lifetime belongs to the physical deployment and equality would be a redundant invariant.
  • Continue duplicating patterns. Rejected because it repeats shared context and can count one edge deployment's physical hardware more than once.
  • Per-bundle activation schedules now. Deferred: they solve staggered rollout but introduce a second temporal dimension and are not needed for the agreed full-lifetime bundles.
  • Per-bundle edge occurrence caches. Rejected because every selected bundle shares deployment timing and context; one aggregate (pattern, need) series plus scalar path shares preserves both physical totals and journey attribution with lower retained memory.
  • A generic containment-inventory framework shared by web and edge. Rejected as premature: web paths carry weights and temporal position, while edge paths carry discrete counts. Keep one simple typed edge inventory and the existing explicit web coordinate mechanism.
  • Compatibility aliases for singular Python inputs. Rejected under the explicit no-backward-compatibility rule; persisted user models are handled by schema migration instead.

8. Constitutional notes

  • The three-layer dependency direction is unchanged: relationship/calculation truth stays in core, persistence migration stays in API utilities, and the interface remains a downstream adapter.
  • Docstrings, parameter descriptions, and computed getter docstrings remain the semantic source of truth; interface tooltips consume them rather than duplicating modeling explanations.
  • The schema change requires a version bump, upgrade handler, and round-trip coverage under the library constitution. No constitutional amendment is needed.
  • No compatibility shim is carried. All co-developed interface callers, templates, fixtures, and examples move to the plural APIs in the same feature.
  • Attribution conservation and exact reactive invalidation are architecture constraints, not optional follow-up work.

9. Open questions

No capability or implementation-strategy question remains. The occurrence/deployment names, web coordinate shape, edge aggregate-cache boundary, containment inventory, and cache-lifetime strategy are resolved for task decomposition.
