Multiple usage journeys per pattern

Status: Spec — approved · 2026-09-01

1. Problem and audience

  • Edge deployments. Industrial users need one deployment cohort to carry several functionality bundles. Today an edge usage pattern points to one edge usage journey, so representing several bundles requires duplicating the deployment context and risks treating one physical deployment as several.
  • Web traffic. Product teams and consultants need one population, location, device, network, and temporal profile to drive several user journeys at different average frequencies. Today they must duplicate the whole usage pattern for every journey.
  • Why now. The one-journey relationship blocks realistic edge models and makes related web journeys unnecessarily repetitive. The two co-developed projects can change the model and interface together without carrying a compatibility shim.

2. Success criteria

  • A web usage pattern always contains at least one usage journey. Each relationship has a strictly positive, possibly fractional weight meaning “average executions of this journey per usage-pattern occurrence”; weights are multiplicities and are not required to sum to one.
  • An edge usage pattern always contains at least one edge usage journey. Each linked journey is one functionality bundle applied once to every deployment represented by the pattern.
  • The lifetime of an edge deployment belongs to the edge usage pattern. Every functionality bundle linked to it is active from deployment until the end of that common usage span.
  • A journey can be reused by zero, one, or several patterns. A web journey can have a different weight in each pattern; an edge journey is evaluated in each pattern's deployment context.
  • Pattern-level country, network, devices, and temporal profile apply consistently to every linked journey. Journeys needing different context or timing use separate patterns.
  • For web patterns, journey weight scales journey concurrency, device occupancy, job calls, network traffic, storage demand, server demand, and their resulting impacts.
  • For edge patterns, functionality-specific needs and server calls add on their shared target devices and components, while the physical deployment, chassis, components, and their fixed footprint are not cloned or counted once per bundle.
  • Reuse is containment-aware: the same step, function, job, or need reached through two journey paths contributes once through each path. Distinct needs targeting the same hardware are aggregated on that hardware.
  • The interface lets users select several journeys, edit web relationship weights, see one canvas relationship per selected journey, and cannot create or leave a pattern without a journey. Creation preselects the first available journey with weight 1.
  • Explainability and impact attribution identify the contributing journey even when a pattern has several journeys or reuses the same lower-level object through several journey paths; Sankey conservation remains exact.
  • Existing one-journey JSON models upgrade without input loss and recompute to equivalent footprint results. New models round-trip with all journeys, weights, deployment spans, sources, and relationships preserved.

3. Scope

Capability-level only. File, class, method, migration-step, and internal-coordinate decisions live in plan.html.
In scope
  • A non-empty weighted web pattern-to-journey relationship.
  • A non-empty, unique, unordered edge pattern-to-journey relationship.
  • Moving edge deployment usage span from the functionality bundle to its deployment pattern.
  • Journey-aware calculations, explainability, comparison, and impact attribution.
  • Creation, editing, relationship visualization, validation, and help text in the interface.
  • JSON schema migration and input-only/calculated-state round-trip behavior.
  • Updates to examples, introductory templates, generated reference descriptions, and the durable architecture documentation that owns relationship and persistence semantics.
Out of scope (this iteration)
  • Weights, adoption shares, or optionality on edge functionality bundles.
  • Staggered functionality rollout: enabling, phasing in, or retiring a bundle during an existing deployment's lifetime.
  • A separate temporal profile, country, network, or device selection per journey inside one pattern.
  • Automatic normalization of web weights or interpreting them as percentages.
  • Cloning journeys or hardware when they are linked from another pattern.
  • Backward-compatible Python constructor aliases or singular relationship shims.

4. UX / interface

The pattern form exposes relationship cardinality directly. These native controls are a conceptual mockup: they show the labels, defaults, and distinction between weighted web journeys and unweighted edge bundles, not the final visual styling.

Web usage pattern

Usage journeys At least one · weights are journeys per pattern occurrence

Example: 1,000 pattern occurrences produce 1,000 browse journeys and 80 purchase journeys.
Edge usage pattern

Functionality bundles At least one · each selected bundle applies once

All selected bundles run on the same deployment for its full usage span.

5. Constraints

  • The library remains the modeling truth. The interface exposes and edits these relationships without reimplementing their calculation semantics.
  • A web pattern's occurrence series is a shared driver. All linked journeys start at the same modeled hour before their weight and internal step timing are applied.
  • An edge pattern's start series counts deployment units or cohorts, not functionality-bundle starts. Device-group multiplicities continue to expand one deployment into its physical device counts.
  • Removing or replacing relationships must preserve transactional recomputation: invalid attempts to remove the last journey are rejected without leaving stale calculated state.
  • The JSON schema change requires a major schema/version increment and an upgrade handler. Incompatible calculated caches may be discarded and recomputed; authoritative inputs must survive.
  • Attribution must continue to conserve each footprint stream exactly while exposing journey identity as part of the containment path.
  • The feature is library-driven and cross-repository: its single specification, plan, and task list live in the library repository, with interface work tracked from the same task list.
