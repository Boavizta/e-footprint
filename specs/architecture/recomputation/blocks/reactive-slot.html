ReactiveSlot technical building block

One slot is the runtime identity of one attribute address in the recomputation graph. Depending on the address, it either caches a computed value or acts as a getter-less change signal for an input or relationship.

Shortest useful model: a slot is simultaneously a cache cell and a graph node. It knows what it read, who reads it, whether its value is current, and how to compute that value—if it computes one at all.

The slot represents an address, not the current value

The value may change repeatedly while the slot remains the graph's identity for that modeling-object attribute. Dependency edges therefore survive replacement long enough to invalidate everything that used the old value.

Every modeling-object instance owns its registry. Two UsagePattern instances therefore have different slots even though their class shares the same computed_attribute descriptor. Dict-backed addresses use an internal composite registry key containing the attribute name and dict key.

Two roles, one node type

Computing slot · getter present
S_utc.getter is a zero-argument getter closure. pull() can run it and cache its result in _value.
Input or membership node · no getter
S_starts and S_country_link compute nothing. A write passes them to invalidate(), which follows their dependents.

What happens when a computing slot is pulled

S_utc.pull()
1 · Cache check
Return _value immediately when cached.
2 · Compute if void
Create a temporary _ComputeFrame, push it on the context-local stack, and call getter(). See Compute stack and ContextVar below.
3 · Commit success
Replace dependency sets with this run's actual reads, update reverse indexes, and cache the result.

The _ComputeFrame is only a passive temporary notebook for one active getter. It contains the slot and two mutable sets; structural read hooks and calculus ancestry recorders find the top frame and add slots to those sets. The frame does not observe or collect anything by itself, and it is not stored beside the slot after computation.

Failure and cycle behavior
  • If the getter raises, the slot stays void and its previous dependency edges remain. This safely over-invalidates until a later successful pull refreshes them.
  • If the active stack already contains the same slot, _compute() raises CircularDependencyError with the recursive slot chain.
  • The context-local stack is reset in finally, so a failed getter cannot leak its compute frame into later work.
  • A getter may read inputs and relationships but may not change them. Attempting invalidation while a computation is active raises instead of mutating the graph midway through dependency discovery.

Compute stack and ContextVar

Dependency recorders can run many calls below the getter that caused them. They need a way to ask “which slot is computing right now?” without passing a frame argument through every domain method. contextvars.ContextVar provides that context-local value: code deep in the call tree can read it, while another thread or asynchronous task gets its own independent value. The exact set-mutation path is explained in How dependency recording mutates the active frame immediately after the annotated excerpt.

The frames were temporary and are gone. Their recorded contents have been copied into the dependency sets on slots B and A.

The stack therefore describes only the getters active right now. At the deepest point above it is the tuple (frame_A, frame_B); after the whole chain completes it is empty again.

There are two returns to distinguish. First, the domain getter returns its value to the getter closure while the frame is still active; this is when the closure records calculus ancestry. Second, the closure returns to ReactiveSlot._compute(); its finally resets the stack, then _compute() commits the populated frame sets.
This preserves direct edges: B records the inputs and relationships B itself consumed; A records B. B's internal dependencies are not copied into A's frame. Invalidation can then travel S_starts → B → A or S_country → B → A through the graph.

This does not depend on B reading only non-computed inputs. If B pulls another computed slot C, the stack temporarily becomes (frame_A, frame_B, frame_C): C records its own inputs, then B records C after C returns, and A records B after B returns. The direct chain remains input → C → B → A.

# Defined once at module level. Each execution context sees its own tuple
# of active computation frames. An empty tuple means “no getter is running”.
_compute_stack = ContextVar(
    "reactive_compute_stack",
    default=(),
)

# The following code runs inside ReactiveSlot._compute(self).
# Here, `self` is the slot whose value is about to be computed.
# If A pulled B, B enters with previous_stack == (frame_for_A,).
previous_stack = _compute_stack.get()

# This passive data container provides two initially empty mutable sets:
# frame.calculus_reads and frame.structural_reads. Dependency-recording
# functions find this frame through _compute_stack and mutate those sets.
# See “How dependency recording mutates the active frame” below.
frame = _ComputeFrame(slot=self)

# Tuples are immutable: this creates a new tuple ending in our frame.
# ContextVar.set() makes it current and returns a token that remembers
# the previous value. For B, the current stack is now [A, B].
# The token itself is NOT inserted into that tuple.
reset_token = _compute_stack.set(previous_stack + (frame,))

try:
    # The stored zero-argument getter closure now runs. Structural read
    # hooks inside it use _compute_stack.get()[-1] to find this frame;
    # before returning, the closure invokes the calculus-ancestry recorder.
    # See “How dependency recording mutates the active frame” below.
    value = self.getter()
finally:
    # reset_token is not removed from the stack: it tells ContextVar to
    # restore the exact value from before set(). The effect is pop-like
    # here: after B it restores [A]; after A it restores [].
    _compute_stack.reset(reset_token)

How dependency recording mutates the active frame

A read hook is a small bookkeeping call embedded in a normal access path. It lets ordinary domain code remain natural while making a structural read visible to the recomputation engine. Two concrete examples are:

Forward-link read
Evaluating pattern.country.timezone traverses the contextual wrapper for pattern.country. Its __getattr__ calls record_read_of_node(pattern, "country").
Reverse-membership read
Evaluating device.parent_groups invokes ReverseCollection.__get__. It calls record_read_of_node(device, "parent_groups") before deriving the current groups.

The calculus path is slightly different: no hook intercepts each numerical Python read. Explainable arithmetic leaves ancestry on the returned value, and the computed-attribute closure inspects that ancestry after the domain getter returns. It is therefore more precise to call it a calculus ancestry recorder or bridge. Both mechanisms ultimately call _record_dependency(...) and mutate the active frame:

def _record_dependency(dependency_slot, read_kind):
    stack = _compute_stack.get()
    if not stack:
        return                         # no computed getter is active

    active_frame = stack[-1]           # the getter currently running
    target_set = getattr(active_frame, read_kind)
    target_set.add(dependency_slot)     # this is what records the read

# Called conceptually as either:
_record_dependency(S_starts, "calculus_reads")
_record_dependency(S_country_link, "structural_reads")

For a normal @computed_attribute, the getter closure triggers the calculus side by calling record_calculus_edges_from_ancestry(result) after the domain getter returns and before the closure returns to ReactiveSlot._compute(). For @lazy_attribute, the parallel closure calls record_calculus_edges_from_value_structure(result) because explainables may be nested inside raw containers.

The final mutation is ordinary Python set mutation. getattr(stack[-1], read_kind) returns the actual set stored on the frame—not a copy—and .add(dependency_slot) changes that set in place. The local frame variable in _compute() still refers to the same object, so it sees those additions after the getter returns.

ContextVar itself is not a stack. The engine stores an immutable tuple in it and implements push/pop behavior by setting a longer tuple and then resetting the returned token. The token is separate bookkeeping created by ContextVar.set(); it is never inside the tuple. reset(token) means “restore the value that was current before this particular set(),” which makes restoration correct after nested calls and exceptions.

The same stack has two jobs. Its top frame receives dependency reads; searching the whole stack before a push detects A → B → A and reports that chain as a circular dependency.

Why edges exist in both directions

Forward reads explain the computation; reverse edges drive invalidation
S_starts
↓ calculus dependency
S_country_link
↓ structural dependency
S_utc
Forward sets contain both dependencies. Each dependency's reverse _dependents set contains S_utc.

replace_dependencies() updates the forward sets and reverse indexes together. A relationship switch can therefore remove the old country's timezone edge and install the new country's timezone edge atomically after a successful recomputation. More generally, every successful run replaces the old edges with what that run actually read, so a dependency from a conditional branch disappears once that branch is no longer taken.

What invalidation changes—and preserves

Changes
_value becomes _VOID; on_value_dropped detaches obsolete computed values; the wave follows _dependents.
Preserves
The dependency sets and reverse indexes remain, allowing later waves to cross void intermediates and reach cached descendants.

_wave_passed prevents repeated invalidation traversal; voidness cannot. Pulling and caching through a slot clears relevant markers so the next change can reach the fresh cache.

What is persisted

The ReactiveSlot Python object, getter closure, cached/void sentinel, and wave marker are runtime-only. Persistence stores slot addresses and dependency edges in the values-free calculation_graph. The load path materializes slots for those addresses and calls replace_dependencies() to rebuild both directions without running getters.
