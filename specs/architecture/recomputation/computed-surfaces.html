Three ways to declare derived state

Modeling authors meet the engine through three class-level descriptors. They share one reactive runtime, but expose different result shapes and update policies.

Choose from the meaning of the result: one modeled result → @computed_attribute; one modeled result per member → @computed_dict; a read-time projection that should not warm eagerly → @lazy_attribute.

Start from the code you write

@computed_attribute
@computed_attribute
def utc_starts(self):
    return self.starts.convert_to_utc(
        self.country.timezone
    )
One attached explainable result for one object.
@computed_dict(keys="jobs")
@computed_dict(keys="jobs")
def energy_per_job(self, job):
    return self.energy_for(job)
One independently cached attached result for every current key.
@lazy_attribute
@lazy_attribute
def impact_rows(self):
    return tuple(
        self.build_rows()
    )
A cached projection, computed only when a consumer asks for it.

What all three share

One declaration model, one runtime graph
1 · Class declaration
Decorator syntax installs a descriptor holding the original domain getter.
2 · Per-instance slot
An instance read resolves one or more ReactiveSlots, each cached or void.
3 · Same dependency graph
Successful computation records dependencies; edits invalidate the affected cache cone.
  • The getter body is the calculation SSOT. For documented computed values, its docstring is the doc-as-code meaning.
  • Each slot pulls recursively, caches a successful result, detects recursive pull cycles, and keeps previous edges after failure as a safe over-approximation.
  • All three participate in the same calculus and structural dependency graph and are invalidated through the same reverse edges.
  • All three may use bare decorator syntax or a parameterized form where supported; the resulting class attribute is a descriptor, not the computed value itself.

@computed_attribute: one modeled value

The descriptor creates one slot per instance and attaches a successful result to the modeling-object attribute address. The returned value must be fresh: returning another attached attribute directly would alias one object into two addresses, so direct reuse requires .copy().

Normal computed output
Reachable outputs recompute when the transaction pulls its configured boundary.
Guard output
A computed output may also explicitly declare guard=True, making its intentional failures surface during the edit transaction even outside the selected eager-output cone.
@computed_attribute technical zoom 🔍Decorator rewriting, descriptor installation, getter closure creation, per-instance dispatch, and storage boundaries.

@computed_dict: one modeled value per current key

@computed_dict(keys="jobs") slot topology
Key-set slot · energy_per_job
Reads the current jobs membership, discards departed keys, pulls current element slots, and maintains facade ordering.
↓ owns and synchronizes
energy_per_job[job_A]
Independent getter, dependencies, cache, and invalidation.
energy_per_job[job_B]
Only this element need recompute when only B's inputs change.
Persistent facade
The same ExplainableObjectDict object survives key-set recomputations.

A whole-dict read structurally depends on the key-set slot. If a key leaves the collection, its sub-slot is removed from the registry and ceases to be a guard; the corresponding facade entry is removed. Previous dependents retain their old edge to that sub-slot only until they successfully recompute.

@computed_dict technical zoom 🔍Key-set slot, stable facade, composite-key element slots, fine-grained invalidation, stale-key pruning, guards, and persistence.

@lazy_attribute: a projection on demand

A lazy attribute is still reactive and cached—it is not a plain property and not functools.cached_property. The difference is policy and ownership: it stays outside calculated_attributes, never participates in eager warming, and keeps its result raw rather than attaching it into modeling-container bookkeeping.

Why value-structure discovery?
A projection may return nested dicts, tuples, sets, or dataclasses. The closure walks that structure and records calculus edges for every contained explainable.
Why lazy?
Attribution matrices and display breakdowns may be expensive and are irrelevant to the main footprint total. They compute only for consumers that need them.
@lazy_attribute technical zoom 🔍Bare and parameterized forms, raw slot caching, recursive value-structure dependency discovery, composition, eager policy, and optional persistence.

Decision guide

Choose the narrowest semantic surface
Does this derived value belong to the model's calculated footprint graph?
Yes → continue with a computed surface. No, it is attribution/display/supporting projection → @lazy_attribute.
↓ if computed
Is there one independently recomputable result per member of a modeled collection?
Yes → @computed_dict(keys="…"). No → @computed_attribute.
Flags refine a surface; they do not create another one. guard=True changes failure timing. serialize=True opts a materialized cache into persistence. Neither changes the underlying dependency mechanism.
Implementation reading route
  1. computed_attribute — single-value descriptor and getter closure.
  2. computed_dict — descriptor class, key-set slot, element slots, facade, and stale-key pruning.
  3. lazy_attribute — raw projection slot and recursive value-structure dependency discovery.
