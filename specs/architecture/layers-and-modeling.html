Layers & modeling

The framework knows how values depend and update. The core knows what environmental footprint means. Persistence knows how systems cross process boundaries.

Constitutional dependency rule: imports point upward only. The framework must remain domain-blind—both in imports and in behavior-bearing names.

Three-layer separation

Foundation at the bottom; peripheral concerns at the top
efootprint/api_utils/
Serialization — how to persist and load. May import both lower layers.
↓ depends on
efootprint/core/
Modeling logic — what is computed. Must not know persistence.
↓ depends on
efootprint/abstract_modeling_classes/
Framework — dependency tracking, explainable values, and incremental recomputation. Must not know domain concepts.

This separation is constitutional (constitution §1.1). core/ is built on top of abstract_modeling_classes/, but it must not import from api_utils/—modeling code should not know how it gets persisted. api_utils/ is the only layer allowed to import from both.

No back-edge, including domain names and hidden behavioral coupling

No back-edge. abstract_modeling_classes/ no longer imports anything from efootprint/core/: the last framework→core leak (a function-local System import in the former computation-chain optimizer) was deleted with the eager push engine when computation became pull-based. Keep it that way.

No domain names in the framework layer. The dependency rule applies to names, not just imports: abstract_modeling_classes/ may not mention core concepts (UsagePattern, Job, Server, …) by name—not in class attributes, strings, or comments load-bearing for behavior. When the framework needs to be polymorphic over a domain-specific extension, it discovers the extension structurally rather than naming it.

Example: @computed_structure in reactive_core/computed_slots.py is the framework-level notion of one arbitrary recursively inspected result cached as a unit; attribution and presentation code use that shape without the framework naming either domain. functools.cached_property is not used on ModelingObjects because derived state belongs in the reactive graph.

What lives in the domain core

Usage
Patterns, journeys, and jobs that define how systems are used.
Hardware
Servers, storage, networks, and end-user devices.
Edge
Devices, components, processes, and groups for fleet modeling.
System
Top-level container; manages usage patterns and computes total footprint.
Framework class map (usually avoid gathering this context for ordinary modeling work)
  • ModelingObject — base class with dependency tracking and update logic. All e-footprint objects inherit from this.
  • reactive_core package — graph.py owns slots, dependency recording, and invalidation; computed_slots.py owns the three computed surfaces; reverse_relationships.py owns ReverseCollection/ReverseLink. Its __init__.py preserves one stable public import surface. See Recomputation.
  • ExplainableObject — manages the calculation graph and automatic explanations.
  • ExplainableQuantity — unit-bearing value; inherits from ExplainableObject.
  • ExplainableHourlyQuantities — hourly time-series.
  • ExplainableRecurrentQuantities — a typical week of 168 recurrent hours.
  • EmptyExplainableObject — neutral numerical object; zero or zero-like time-series.
  • ModelingUpdate in modeling_update.py — transactional update and recomputation boundary.
Builders and modeling templates

efootprint/builders/ provides convenience subclasses of core objects with sensible defaults and external-data integrations such as EcoLogits and Boavizta.

efootprint/modeling_templates/ ships reference systems backing the mkdocs how-to pages: JSON under how_to/, regenerable Python authoring scripts under how_to/_authoring/, and a typed registry (HowToTemplate, HOW_TO_TEMPLATES). A separate HowToGuide/HOW_TO_GUIDES registry maps each how-to page (doc_path) to the template_id it walks through. This is decoupled from the loadable template, so several guides can share one scenario (the database and server-to-server guides both point at ecommerce), and HowToTemplate itself carries no doc_path.

Public helpers list_how_to_templates, list_how_to_guides, get_template, and load_template_system live on the package; imports remain upward-only through api_utils for load/save. Template authoring uses efootprint.builders.timeseries builders for input hourly/recurrent timeseries so those inputs stay editable in the interface after JSON load.

Modeling-object shape

One domain class: inputs + formulas + activation
default_values
Numerical defaults and the units used for consistency checks.
Decorated getters
One @computed_attribute or @computed_dict getter per derived value; body is formula, docstring is meaning.
after_init
Enables live updates through trigger_modeling_updates.

calculated_attributes is derived from the class computed-slot registry (computed_slots(cls)); a subclass drops an inapplicable inherited attribute with removed_computed_attribute(). Computation itself is documented in Recomputation.

Class registration and ordering

RegistryPurpose
ALL_EFOOTPRINT_CLASSESEvery concrete ModelingObject subclass: core, builders, and services. JSON uses it to resolve class names round-trip.
CANONICAL_CLASSESTop-level core families every object maps to through canonical_class. Derived from flattened SANKEY_COLUMNS plus SANKEY_BREAKDOWN_ONLY_CLASSES and NON_SANKEY_CANONICAL_CLASSES. It is membership only; pull-based computation needs no class ordering.

SANKEY_COLUMNS, OBJECT_CATEGORIES, and per-shape lists such as SERVER_CLASSES and EDGE_COMPONENT_CLASSES live alongside them and are consumed by rendering and builder code.

Checklist: add a modeling object
  1. Inherit from the appropriate core or builder base.
  2. Define default_values.
  3. Implement a decorated getter per computed attribute.
  4. Add the class to ALL_EFOOTPRINT_CLASSES; for a new top-level core family, extend SANKEY_COLUMNS, SANKEY_BREAKDOWN_ONLY_CLASSES, or NON_SANKEY_CANONICAL_CLASSES.

This is a constitutional quality gate (§2.5).

Units, display, and doc-as-code

All quantities use Pint. Custom units live in efootprint/constants/custom_units.txt. Calculations remain explainable with full dependency graphs. Pint quantities flow through calculations unchanged; magnitude-aware scaling happens only at render time via efootprint/utils/display.py's best_display_unit() and format_quantity_for_display(). Explainable classes expose display_quantity and display_unit.

Doc-as-code metadata contract

Per constitution §1.4, descriptive metadata about classes, parameters, and calculated attributes lives in the classes, not external documents. This SSOT migration has shipped; the contract below is live.

  • Class docstring — what the class is.
  • param_descriptions — one entry per __init__ parameter except self and name.
  • Computed getter docstring — what the calculated attribute means.
  • Optional disambiguation, pitfalls, interactions, and param_interactions.

The mkdocs reference and e-footprint-interface consume this metadata; descriptions are not duplicated elsewhere.
