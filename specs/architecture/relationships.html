Architecture / Relationships

Object relationships

Links do two jobs at once: they make a navigable model and they create structural dependency nodes that keep pull-based computation correct when membership changes.

One graph: calculus edges from arithmetic and structural edges from relationship reads meet in the same slot-addressed reactive graph.

Three relationship types

Ways one modeling object can own or reference another
Direct
self.child = object
A single contextual reference.
List
ListLinkedToModelingObj([...])
An ordered collection of contextual references.
Structural input dict

Modeling-object keys represent children; values may carry relationship data.

All three populate contextual_modeling_obj_containers on children so they can discover parents. Dict relationships are additionally discoverable through explainable_object_dicts_containers. Relationship read hooks record structural edges; writes invalidate the membership node and bump affected reverse-relationship nodes at the container-field transition.

Declarative reverse relationships

ReverseCollection and ReverseLink expose typed reverse views over modeling_obj_containers. They remain framework-level declarations: framework behavior discovers relationships structurally without naming domain classes. Reading them during a computation records the corresponding structural dependency; link transitions invalidate their nodes.

Traversal SSOT: mod_obj_attributes

Downward traversal must call mod_obj_attributes. It returns every referenced object across direct, list, and structural-input-dict relationships. Consumers include the relationship-graph builder and e-footprint-interface cascade deletion.

Wrappers, deletion, and the calculated-dict exclusion

Direct and list references are wrapped in ContextualModelingObjectAttributes; structural dict keys are the ModelingObjects themselves. contextual_mod_obj_attributes exposes the wrapped subset for its one specialized caller, self_delete, which severs those links one by one and leaves dict-held children to the dict, which unlinks its keys together.

Only structural input dicts count as references. Calculated dicts keyed by modeling objects—such as Job.hourly_occurrences_per_usage_pattern or Storage.full_cumulative_storage_need_per_job—are results. Treating those keys as links would incorrectly make every result-holder a container of its result keys.

ExplainableObjectDict: input versus calculated

ModeMutation boundaryReactive shape
Calculated dictThe computed-dict descriptor owns attachment and removal through its facade; these framework writes are passive.The facade presents one key-set node plus independently cached per-key sub-slots.
Input dictAn unattached dict or one attached to an object still under construction/hydration mutates passively. Once its owner is live, every public set/delete routes through ModelingUpdate.Keys are structural children when they are modeling objects; reads/writes participate in the dependency graph.
Explicit passive storage and critical deserialization order

ModelingUpdate.apply_changes() and rollback call private passive list/dict primitives that perform complete forward-link, reverse-link, ordering, and structural-node bookkeeping without recursively launching another update.

During deserialization, input dicts start empty on hydrating owners. A deferred loop populates them through the same passive storage boundary; stored values, ancestry links, and serialized dependency edges are restored before every object becomes live together. Loading therefore never computes or exposes a partially transactional graph.

Weighted relationship dicts and ordering

Relationship dicts whose values are weights—UsageJourney.uj_steps, UsageJourneyStep.jobs, RecurrentServerNeed.jobs, and EdgeDeviceGroup.sub_group_counts/edge_device_counts—use to_weighted_explainable_object_dict. It accepts duplicate keys in a list (accumulating counts) or plain-number dict values (wrapped as dimensionless SourceValues), and returns WeightedExplainableObjectDict, which enforces dimensionless, non-negative weights on every set.

JSON rebuilds dict attributes using the class declared by their constructor annotation, so the subclass and invariant survive round-trips. ModelingUpdate and structural replacements preserve the dict type. Calculations read weights with .items()—for example, journey duration is Σ times-per-journey × step time; iteration returns related objects in insertion order, preserving journey-step ordering.
