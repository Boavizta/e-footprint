Architecture / Recomputation

Reactive computation, from modeling code outward

Modeling authors declare derived state with three decorators. The engine gives all three the same pull, cache, dependency, and invalidation mechanics, then varies caching and result shape by surface.

Shortest useful model: declare a getter; the first read computes and caches it while discovering what it used; an edit drops only affected caches; a later pull rebuilds what is needed.

What the engine shares across all three

One lifecycle underneath three author-facing APIs
1 · Declare
A decorator installs a class-level descriptor around the domain getter.
2 · Pull
An instance read resolves a per-instance slot and returns its cache or runs its getter.
3 · Discover
The successful computation records the values and relationships it consumed.
4 · Invalidate
An edit sends a deletion wave through reverse dependency edges.
5 · Recompute
Configured boundaries or later explicit reads pull void slots again.
Calculus dependencies
The result consumed a numerical or explainable value. Explainable formula ancestry maps that value back to its stable slot address.
Structural dependencies
The getter traversed an object relationship or collection membership. A structural read hook records that address directly.

Both edge kinds live in the same per-instance slot graph and trigger the same invalidation behavior. Reading self.country.timezone, for example, depends both on which Country is linked and on that Country's timezone value.

The common runtime object: ReactiveSlot

A ReactiveSlot is simultaneously a cache cell and a dependency-graph node for one stable attribute address. Computing slots have getter closures; input and membership nodes have no getter and act only as invalidation sources.
